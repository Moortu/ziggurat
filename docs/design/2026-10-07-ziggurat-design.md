# Z.I.G.G.U.R.A.T: design (revision 11)

Status: draft, revised after three independent reviews, the Stage 0 spikes, Stages 1 to 6, Stage 7a and Stage 7b (section 16). Date: 2026-10-07; revision 4: 2026-10-13; revision 5: 2026-10-14; revision 6: 2026-10-20; revision 7: 2026-10-21; revision 8: 2026-10-23; revision 9: 2026-10-24; revision 10: 2026-10-26; revision 11: 2026-10-27. The project is named Ziggurat, styled **Z.I.G.G.U.R.A.T** in titles and branding (after Projekt J.E.N.O.V.A). Dots are display only: every identifier, file name, package name and Godot class name is plain lowercase `ziggurat`.

Pins: Zig 0.17.0, Godot 4.7.2 (single precision only), gdzig commit `c8e0768` (2026-10-05), vendored with five patches: two comptime branch quotas, a build option that withholds the Object helpers from scripts, gdzig's own class checks in place of the unlicensed `oopz` package, and acquire and release ordering for the lazy caches (`vendor/gdzig/PATCHES.md`, section 13). All are enforced at load time (section 3). Exported Linux games target glibc 2.28 (`x86_64-linux-gnu.2.28`, the highest version the official 4.7.2 Linux template needs; section 4); exported Windows games target `x86_64-windows-gnu` (MinGW ABI, Universal C Runtime, no MSVC runtime).

How to read claims: **verified** means someone ran it or read the cited source; **speculation** is labeled as such.

## 1. Goal and non-goals

**Goal.** Do for Zig what Projekt J.E.N.O.V.A does for C++: write `.zig` scripts inside a Godot project, attach them to nodes like GDScript, have the editor compile them, and hot-reload them without restarting. gdzig provides the Godot bindings. This project writes no bindings; it is the integration layer on top of gdzig.

**Distribution.** Ziggurat ships as an ordinary add-on in `addons/ziggurat/` for stock Godot 4.7.2: one zip with the extension library for every supported platform, published on the Godot Asset Store (the store the 4.7 editor uses) and as a release download with the same contents. No installer program and no engine fork. The old Asset Library is deprecated and the 4.7 editor no longer reaches it. The zip never contains the Zig compiler: the Asset Store rejects standalone executables, and Zig is 54 to 96 MB per platform. Exported games contain neither Zig nor the editor parts. Details in `../research/integration-distribution.md`.

**The package as built** (Stage 6; layout and sizes of Stage 7b). `zig build package` writes `ziggurat-<sdk_version>.zip` (version 0.1.0: `ziggurat-0.1.0.zip`, about 31.3 MB or 29.9 MiB, 2298 files, about 330 MB unpacked; Stage 7a, Linux only: 15,562,438 bytes and about 164 MB; Stage 6: 14,401,102 bytes and about 136 MB, before gdzig patch 5 turned the cache reads and writes in the generated bindings into longer atomic ones). One zip holds every supported platform (the user's decision of 2026-10-26). Its root is `addons/ziggurat/`, because Godot's installer keeps an `addons/` root:
- `LICENSE` (MIT, with its copyright line), `README.md` (install, Download Zig, debugging, export), `THIRD_PARTY_LICENSES.md` (section 13), `gdzig-PATCHES.md` (the list of gdzig patches that `THIRD_PARTY_LICENSES.md` names, a copy of `vendor/gdzig/PATCHES.md`) and `ziggurat.gdextension`;
- the editor libraries `bin/libziggurat_host.so` and `bin/ziggurat_host.dll`;
- per target key (section 4), in `bin/<key>/`: the export host as a static archive (`x86_64-linux/libziggurat_host_export.a`, `x86_64-windows/ziggurat_host_export.lib`) and the game library for a project without Zig scripts (`x86_64-linux/libziggurat_game_empty.so`, `x86_64-windows/ziggurat_game_empty.dll`, section 10);
- the SDK as source per target key, `sdk/x86_64-linux/` and `sdk/x86_64-windows/`, each with its own `sdk-manifest.json`, and `sdk/.gdignore` (section 5). The two SDK copies differ in one file, the translate-c output `gdextension/gdextension_interface.zig`.

This version holds Linux x86_64 and Windows x86_64 libraries; macOS is Stage 7c. The editor libraries in the package are ReleaseSafe, LLVM and stripped, built for `x86_64-linux-gnu.2.28` (so the Linux one loads on any glibc from 2.28) and `x86_64-windows-gnu`, and hold no checkout path; `zig build host -p <project>` (development) still installs a Debug editor library with debug info for `-Dtarget` into the same layout. The package is deterministic: entries sorted, fixed time and mode, no directory entries; two packager runs, two separate checkouts and two cache folders (relative or absolute, `--cache-dir`) give the same bytes (section 11). It holds no executable (every ELF file is a shared library without an interpreter, and every PE file is a DLL), no `zig` or `zig.exe`, no repository, cache or Nix store path, and no `.gitignore`-style files the Asset Store asks authors to remove. The Windows DLLs are not code-signed (the user's decision of 2026-10-26). There is no `plugin.cfg`: the editor plugin is added by the extension itself (section 7), so it cannot be switched off in Project Settings > Plugins. The release zip and the Asset Store upload are the same file.

**Non-goals for v1.**
- No new bindings and no gdzig fork. The vendored copy carries only the patches listed in section 13; fixes go upstream.
- No macOS support yet (Stage 7c). Linux x86_64 came first; Windows x86_64 is supported since Stage 7b, but tested under Wine only, never on a real Windows machine (section 2, risk 35). Every decision keeps macOS in mind (section 4).
- No Windows arm64 or 32-bit x86, and no other Linux architecture in the package.
- No custom Godot builds. Ziggurat is an ordinary add-on for the stock engine (section 1, Distribution).
- No network library linked into the extension. The Zig download (section 9) uses Godot's own HTTP client, and exported games never download anything.
- No script-to-script inheritance. Nothing in the table is reserved for it; adding it later is a new ABI version (section 3).
- No safe unloading of old module generations (section 6).
- No Godot version other than 4.7.2, and no double-precision builds.
- No native threads or `WorkerThreadPool` tasks started from user code (section 6).

## 2. What the research and reviews established

Full reports are in `../research/` (private workspace, next to this repository). Facts that drive the design:

**J.E.N.O.V.A** (`jenova-runtime.md`). A full script backend, not a GDExtension wrapper: `ScriptLanguageExtension` plus `ScriptExtension` plus `script_instance_create3`. All scripts compile into one library. Its "interpreter" exists only because C++ cannot generate call wrappers, so signatures are recovered after linking (linker MAP files on Windows, `gdb` on Linux) and called through a runtime FFI. Problems we do not copy:
- one shared memory slot per property, swapped in and out around every call (not reentrant, not thread-safe);
- reload unloads the old module before loading the new one, with no rollback; on Linux old modules are never unloaded and are loaded with `RTLD_GLOBAL`;
- the build busy-waits on the main thread, and compile errors never reach the script editor;
- `_validate` and all debugger hooks are stubs; scripts work only on Node owners; no placeholders, no inheritance;
- most user-reported problems come from networking and package-manager code linked into the extension;
- its module runs its own godot-cpp with the host's library token and casts objects across the two godot-cpp copies. Our design avoids that because gdzig engine classes are opaque (an engine object is just its Godot pointer; no per-object wrapper data).

**Godot 4.7.2 script contract** (`godot-script-contract.md`, plus review). Key points:
- `Object::get_script()` returns `script_instance->get_script()`, so the instance must hold a strong reference to its Script. A null `_instance_create` result silently drops the script.
- Nearly every virtual is "required", but nothing checks that at load time. A missing one logs once and returns zero. Some zero returns do damage: a null `_make_template` crashes the Create Script dialog, and the default `_auto_indent_code` replaces user code with an empty string.
- `script_instance_create3` keeps the info table pointer without copying it, so the table must be static.
- A null `refcount_decremented_func` leaks every RefCounted object that carries the script.
- `callp` receives an uninitialized call-error struct. Always set it. `INVALID_METHOD` is the only code that falls through to engine methods.
- In the editor, non-tool scripts get placeholder instances. Scene values survive saving only if `_has_property_default_value` is true for them. While a script is broken or has no descriptors, `_is_placeholder_fallback_enabled` must be true, otherwise saving the scene drops every script value and signal connection. Even then, a connection to a script-declared signal survives only if the script reports that signal: from its descriptors or, without any, from a text scan of the source for signal names. A bound connection to a method of a broken script is dropped when the scene loads; GDScript behaves the same (verified in Stage 3).
- The engine enables processing only if `has_method` reports `_process` and friends, and only at READY.
- **`_frame` is not a safe point.** `Main::iteration()` runs nested inside functions a script can call (for example `EditorInterface.make_mesh_previews` calls it twice, `editor_interface.cpp:218-219`), and every nested iteration calls `language->frame()` (`main.cpp:5107`). Re-checked: verified.
- Recovery mode loads no GDExtensions (`gdextension_manager.cpp:115-117`, re-checked), so a panic that kills the editor can leave the project unopenable with our language.
- `_get_global_class_name` runs on the file-scan thread and can only parse text cheaply. Duplicate global class names overwrite each other silently.
- GDExtension `reloadable = true` does not update script-instance tables that live in the unloaded library. A language extension must ship `reloadable = false`; user code reloads as a separate library (the way C# does).
- On save, the editor tells the running game to reload scripts immediately (`script_editor_plugin.cpp:768`). The game is a separate process. Only the script editor's save does this for an external `.zig` file (`resource_saved` -> `_res_saved_callback` -> `trigger_live_script_reload`, `script_editor_plugin.cpp:723-799`), and only when Debug > Synchronize Script Changes is on and the language's `_validate` reports the file valid (:777-783). A scene save live-reloads only built-in scripts of that scene (:749-758). So `_validate` must report valid for a script whose last build succeeded. Verified under Xvfb in Stage 3 (`zig build test-gui`).
- 4.7 falls back to a plain-text highlighter unless an `EditorSyntaxHighlighter` is registered for the language (#121288 open; not verified in source). Stage 5 registers one (section 9).
- `EditorPlugin._build()` runs on the main thread when Play is pressed, after the open scenes and scripts are saved, and the run waits for its answer; `--build-solutions` calls it once and exits with status 1 when it returns false (Stage 5).

**Zig 0.17.0** (`zig-integration.md`, plus review; x86_64 Linux unless stated):
- `std.DynLib` has no Windows implementation. On Linux without libc it uses Zig's `ElfDynLib`, which does no relocations, TLS or init and segfaulted on first thread-local access. We write our own loader. Modules link libc.
- gdzig builds and passes its in-Godot test suite (133/133) with the self-hosted backend. Incremental rebuild after a function-body change took 14 to 26 ms; LLVM took 3.6 s.
- **Incremental warm-up is expensive** (review, 300 synthetic scripts with 30 fields and 30 methods each): non-incremental cold build 5.4 s; first incremental update 86 s; the same again after a compiler-server restart 80 s (no state survives); later body edit 20 to 26 ms; later field-default edit about 265 ms. Small gdzig-only projects warm up in 14 to 20 s. Stage 0 measured with a different generator and found shorter warm-ups but slower body edits at 300 and 1000 scripts (section 12).
- Incremental builds have broken debug info (gdb and lldb). Non-incremental builds work with lldb.
- Windows self-hosted DLLs crashed under Wine (not tested on real Windows). macOS incremental linking panics.
- Compile errors come back as a binary `ErrorBundle` over `--listen`, decodable with `std.zig.ErrorBundle`. **Errors raised inside SDK code point at the SDK's file** (for example `ziggurat.zig:92`) with "called at comptime here" notes, not at the user's line.
- **A module can import only files below its root file's folder** (`error: import of file outside module path`, re-checked). A root file in the cache folder cannot import project files. Also, a file may belong to only one module, so one module per script fails when scripts share helpers.
- The compiler's output file is rewritten in place by incremental builds and left as partial garbage after failed builds. Never load it directly.
- Each module file is about 15 MB (24.6 MB incremental), plus 256 KiB of thread-local storage per thread that touches it. 100 reloads take about 2.5 GB on disk.
- `@typeInfo` is struct-of-arrays (`field_names`, `field_types`, `field_attrs` with `defaultValue()`, `decl_names`). `decl_names` lists only `pub` declarations. Parameter names are unavailable. Unused function bodies are never analyzed, so compile-time checks do not cover them.
- A panic in user code aborts the process; recovery is impossible. gdzig ignores a user's `pub const panic`.
- `std.fs.getAppDataDir` was removed. Per-OS directory logic is ours.
- Export: iOS and web cannot practically load a separately compiled module; link everything into one library per platform.

**gdzig behavior across two copies** (review, verified by source and experiments):
- Godot does not call into a user copy because of the host's library token. Opaque classes need no instance bindings, and `Object.destroy`'s binding is freed in the same call.
- All Variant, String, StringName, Array and Dictionary values live on the engine heap (`engine_allocator` has no state), so any copy can free them. Memory from a copy's own Zig allocator or pools must be freed by the same copy.
- `StringName.fromComptimeLatin1` returns a cached static name that must never be `deinit`ed. Doing so double-frees; Godot then prints "Unreferenced static string" while holding the StringName table lock, calls our `_debug_get_current_stack_info`, which creates a StringName, and **deadlocks**. This was the hang and the "ObjectDB leaked" warning in the spike, found with gdb. gdzig has the same bug (`Callable.mixin.zig:24-25`).
- gdzig Variant helpers are unsafe at the boundary: `Variant(Resource).as(*Node)` returns a non-null pointer; `as(*Node)` on a freed node returns a dangling pointer; scalar `f32`, `i32`, `u64` do not compile; enum conversion from an out-of-range int panics; `Variant.init` on a fresh RefCounted leaks it (init refcount 1 plus one added by the Variant).
- Lazy caches (method-bind pointers, static names) are written without atomics and race under threads.
- `classdbGetMethodBind` returns null when no method matches (custom engine builds), and ptrcall dereferences it.

**Spike** (`../research/spike/`, Godot 4.7.2 headless): a gdzig host registered "Zig" as a script language; Godot created instances through our `ScriptExtension` and `script_instance_create3` and delivered `READY`; a separately built library used gdzig in bindings-only mode with the host's entry point and renamed real nodes; two copies loaded at once. gdzig needs `@setEvalBranchQuota(100_000)` in `virtualMethodNames` for classes with many virtuals (the spike used a patched copy). On a project's first editor start Godot itself segfaults during extension doc generation (a deferred call runs after `EditorHelp::cleanup_doc()`); this is godotengine/godot#111645 and #111048, fix PR #123658 open. Workaround: pre-create `.godot/extension_list.cfg`.

**Stage 0 spikes** (`../research/stage0/`, one `RESULT.md` per spike; Zig 0.17.0, Godot 4.7.2, x86_64 Linux). Verified:
- **Root location** (`s1-root/RESULT.md`). A hidden generated root `<project>/.ziggurat_root.zig` builds a multi-folder project, also with spaces, non-ASCII letters, `"` and `\` in paths. Godot's file scan skips dot-files, so the root is not in the filesystem cache and gets no `.uid`. The scan honors `.gdignore` but does not skip `addons/`. A read-only project builds from a mirror copy in the cache folder, with error paths mapped back (section 5).
- **Warm-up** (`s2-warmup/RESULT.md`). Numbers in section 12. **An `@export` inside a generic function goes stale under incremental compilation:** after a field change in a script, the `ziggurat_describe` exported from the generic SDK function still pointed at the old table and code, and the update reported 0 errors. A non-incremental build of the same sources passes, and so do exports declared in the generated root (tested at 50 scripts; section 5). Incremental outputs are sparse files about 2.7 times the size of a non-incremental build (677 MB apparent size at 1000 scripts).
- **Generation swap and migration** (`s3-swap/RESULT.md`). Two gdzig copies; fields moved by name and type, dropped fields logged, the `migrate` hook, the old `deinit`; a same-layout swap keeps the data pointer; a swap requested inside a script call waits for `_frame`; instance data and the user heap end at 0 bytes; 20 runs out of 20. The strong-reference fix holds: `get_script()` is non-null after `set_script` and after a swap. **A half-truncated `.so` passed `dlopen` and ran** (the cut removed only debug sections and the section headers), so the loader checks ELF completeness before loading, with checked arithmetic: an unchecked sum on a corrupt header crashed the Debug host.
- **RefCounted objects made from Zig** (host check). An object made with `ScriptExtension.init()` already holds one counted reference and `refcount_init` is spent, so Godot's `Variant(Object *)` constructor adds a second one. The creator drops its creation reference after building the Variant; otherwise the script leaks at exit.
- **Game-process reload** (`s4-game/RESULT.md`), with a fake editor that speaks the real remote debugger protocol. `reload_scripts` arrives as `_reload_scripts(scripts, soft_reload=true)` at the end of the game's frame; `reload_scripts` with an empty path list never reaches the language. The manifest flow swaps, keeps the generation when the build is not staged yet, and rejects bad manifests (section 6). `_reload_scripts` and `_add_global_constant` are required virtuals in 4.7.2. **Debugger packets must be written from one buffer:** `StreamPeer.put_var` writes the length and the payload in two writes, and the game drops the connection.
- **Stripped-source export** (`s5-export/RESULT.md`). Section 10.
- **GUI editor** (`s7-gui/RESULT.md`, automated, on a virtual X display). The host loads, Create Script offers Zig, a tool script swaps live in the edited scene, and a scene saved after the swap keeps the swapped values. A null `_make_template` crashed the editor (signal 11 in `ScriptCreateDialog::ok_pressed`). Without a pre-created `extension_list.cfg` the GUI first start does not crash, but Create Script lists Zig only after a restart. Saving a scene saves every open script, and the editor rewrites `.zig` files with tab indentation (`convert_indent_on_save`). Non-tool Zig scripts ran inside the editor, both during `--import` and in the GUI editor, because the spike host has no placeholder instances. gdzig's comptime branch quota blocks five more `ZigLanguage` virtuals (section 7).

**Not run in Stage 0:** Windows (deferred to stage 7) and macOS; double-precision builds; thread races (the spike gate used a single-threaded lock); nested `Main::iteration()` during a swap; a release (not Debug) export build; the six manual checks of the GUI editor on a real desktop (`s7-gui/MANUAL.md`).

**Stage 3** (the real host, headless and under Xvfb). Verified:
- The script editor's save of a `.zig` file reaches the running game's `_reload_scripts` (above).
- Zig 0.17 accepts leading tab indentation, so files the editor rewrites with tabs still compile. A tab inside comment text or a multiline string literal does not compile; the editor converts only leading indentation.
- With the real SDK, warm-up and edits cost several times the Stage 0 numbers (section 12).
- `_lookup_code` returns `ERR_UNAVAILABLE`: `OK` with an empty result makes the script editor treat every word as a symbol (`script_text_editor.cpp:1208,1319`).

**Stage 4** (reload, headless editor and game, and under Xvfb). Verified:
- `EditorInterface.make_mesh_previews`, called from a GDScript signal handler while a Zig method is on the main thread's stack, runs `_frame` nested twice. The swap waits for a later frame (`zig build test-stress`, section 6).
- The save-triggered `reload_scripts` reaches an editor-launched game before the editor has staged the build. Stage 4 made the game poll the manifest; Stage 5 replaced the polling with the editor's own reload message (section 6).
- **Zig 0.17 incremental mode kept stale code after a layout change.** The SDK's `get_default` took a field's address from the comptime defaults image (`&@field(defaults, name)`). After an incremental update that changed the script's struct layout, the update reported 0 errors, but `get_default` still used the old field offsets: it returned another field's bytes and crashed on owned text fields. Reading the field from a run-time copy of the image fixes it. The host also compares the defaults after each editor load (section 5). Section 13 has the upstream status.
- An incremental update can leave a script's layout hash changed although its file did not (a dependency changed); the build service then rebuilds in full (section 5).

**Stage 5** (the editor plugin and the Zig download; headless editor and game, Xvfb, and one real download outside the tests). Verified:
- `Engine.is_editor_hint()` is already true at the EDITOR initialization level in the editor, so the host adds its editor plugin there only in the editor; a game started from the editor binary registers the editor classes but gets no plugin (host test `no plugin in a game`).
- A message capture that the game registers from Zig (`EngineDebugger.register_message_capture` with a Callable on a host class) receives the editor's `ziggurat:reload` message in an editor-launched game (under Xvfb, `zig build test-gui`). A game reads the manifest at start, but the editor accepts its debugger connection a frame or more later, so the editor resends the last generation when a session starts (section 6).
- Godot 4's `String` stores one 32-bit code point per character, so `CodeEdit` columns count code points, not UTF-16 units (section 9).
- `HTTPRequest` with `use_threads` on: `cancel_request` joins the transfer thread, which blocks in a read while a mirror sends nothing, so cancel and editor exit froze the editor. The download polls its transfers on the main thread instead (section 9).
- Zig 0.17's `std.compress.xz` decompressor cannot be peeked (an assertion in the buffer rebase), and a stream cut at a block boundary reads as a normal end; `std.tar` also takes a missing end marker as the end. So a cut archive would unpack "complete" unless the install requires the xz index and footer, which it does. Block checks (CRC) are not verified by std; the whole file is checked by SHA-256 and signature first (section 9).
- The real `zig-x86_64-linux-0.17.0.tar.xz` (57 MB, one xz block of 372 MiB) installs in about 5.5 s with a peak resident memory of about 893 MiB; the real `.minisig` verifies with the pinned key, and the same file requested under another archive name fails the `file:` check (manual run outside the tests).
- Every RefCounted object that a gdzig call returns (a Godot `Ref` return) carries a reference for the caller, and gdzig's `init()` already takes the first reference on a new RefCounted; the host releases the first and never adds a second (the leak scans catch both).

**Stage 6** (export and package; headless editor, the official 4.7.2 export templates, exported games run headless). Verified:
- The official 4.7.2 `linux_release.x86_64` and `linux_debug.x86_64` templates need glibc symbol versions up to `GLIBC_2.28` (`readelf -V`), so exported game libraries target `x86_64-linux-gnu.2.28` (section 4).
- Zig 0.17 bundles compiler_rt into neither an object nor a static library, only into the final shared library, so the export host archive and the module link into one library with one compiler_rt and no duplicate symbols. Each compilation's std code stays local, and the host's gdzig (with the Object helpers) and the scripts' gdzig (without) live in one library and work.
- Debug information holds absolute paths (14 in a two-script export library), so two project folders gave different bytes; with `-fstrip` the libraries were byte-identical and held no path (section 5). A Zig static archive names its member after the object's path in the build cache, `<cache dir>/o/<cache hash>/<name>.o`: the hash differs per checkout, and with an absolute `--cache-dir` the name is the absolute cache path; the object bytes are the same (section 13).
- `EditorExportPlatform.add_message` with an error does not fail an export by itself: a headless export ends "completed with warnings" with status 0. A library that a `.gdextension` template key names but that does not exist fails it: Godot's GDExtension export cannot copy it ("Failed to copy shared object"), the export fails and a headless export exits with status 1. Godot writes `<game>.x86_64` and `<game>.pck` before that copy, so a failed export leaves them in the output folder. The same missing library failed every export of a project that has the add-on but no Zig scripts (section 10).
- The exported game converts scenes to binary at export; a scene that names a script only by uid (with a wrong text path) and a script that is not in the pack still load through the linked registry (section 10). This closes the open gaps of the Stage 0 export spike: the release (not Debug) build and uid references with stripped sources.
- The `oopz` package, which gdzig used for its class checks, has no licence (no licence file at the pinned commit or later, none in the README, the GitHub API reports none), so it could not be redistributed; it is replaced (section 13).

**Stage 7a** (Linux hardening; headless editor and game, lldb 21.1.8). Verified:
- Zig 0.17's self-hosted aarch64 backend cannot build a ten-line file (`zig build-lib -fno-llvm -target aarch64-linux-gnu`: `error: too big mul_safe i32`), so aarch64 Linux stays on LLVM without incremental mode (section 5).
- lldb reads an LLVM Debug build fully (file, line, `frame variable`). On a self-hosted non-incremental build it stops at file and line breakpoints and shows the stack, but warns `no plugin for the language "zig"` and shows no variables; incremental builds have broken debug information (above). A pending `file:line` breakpoint resolves when Godot loads the module. With `ptrace_scope` 1 (common on Linux) a debugger may attach only to its own child processes.
- `dlclose` of a Zig module (`-lc`, a thread-local) returns 0 and removes every mapping of it, so glibc can unload modules (safe unloading stays deferred, section 6).
- ThreadSanitizer works with Zig 0.17 (`-fsanitize-thread`), but the test runner still exits 0 after a race report unless `TSAN_OPTIONS=halt_on_error=1` is set. It found real races in the lazy caches of gdzig (`fromComptimeLatin1`) and the SDK (`StaticName`): two threads wrote the multi-byte value at once (section 13).
- A headless editor can Play a headless game when `editor/run/main_run_args` is `--headless`, so a game session from the editor runs inside `zig build test`.
- `-freference-trace=16` on every editor build costs +0.4 % on the median body edit at 300 scripts (135.5 against 136.0 ms, six alternating rounds each).
- A change check that finds nothing takes 21 ms (median of 10) at 1000 scripts, on the build thread.

**Stage 7b** (Windows x86_64, under Wine 11.19 only; no real Windows machine, the user's decision of 2026-10-26; Godot 4.7.2's official Windows editor and export templates). Verified:
- **Wine and file locks.** Zig 0.17's std locks a file on Windows with `NtLockFile` and an I/O status block, and Wine 11.19 answers that with `STATUS_NOT_IMPLEMENTED`. kernel32 `LockFileEx` works under Wine, so Ziggurat's own locks use it (section 4). The Windows `zig.exe` 0.17.0 locks its cache manifests the std way, so **under Wine it compiles nothing** (`checking cache failed: manifest_create Unexpected`; `zig.exe version` works). No Ziggurat change can avoid this. So a Windows editor that builds Zig scripts, or exports a project with Zig scripts, is **unproven even under Wine**: the tests reach the point where `zig.exe` starts and stop there (section 11, risk 35).
- **Proven under Wine:** a Windows export from the Linux editor (the game runs its two Zig scripts under Wine); the Windows editor loads the host, finds the Windows Zig and prepares the build; the Windows editor exports a Linux game from a project without scripts; the Windows Zig download installs the real 100 MB zip with the pinned hash and key; the old-game-library rule (section 10); locks, the generation store with its trash folder, process trees in a Job Object, the loader and the PE check, in Zig's Windows unit tests (`zig build test-windows`).
- **Godot's Windows editor loads a copy of every GDExtension DLL** (`platform/windows/os_windows.cpp:490-522`): it copies `bin/ziggurat_host.dll` to `bin/~ziggurat_host.dll` (hidden attribute), loads the copy, and deletes a left-over copy before the next copy. So the add-on's DLL can be replaced while the editor runs, but a `~ziggurat_host.dll` stays next to it (risk 38).
- **MinGW runtime exports.** A Zig `x86_64-windows-gnu` DLL linked with libc exports `_CRT_INIT`, `__mingw_module_is_dll` and `atexit` besides its own exports. A module-definition (`.def`) file that lists only `ziggurat_host_init` removes them; it does not remove a `dllexport` the code declares, so the generated root of a Windows export also marks `ziggurat_describe` and `ziggurat_init` hidden. Both together give a DLL that exports exactly `ziggurat_host_init` (section 3).
- A Windows debug build (`-fno-strip`) writes its debug information to a separate `.pdb` file in the build cache; the DLL holds only the `.pdb` file name, no section with build-machine paths.
- std's `Child.kill` on Windows calls `ntdll.RtlReportSilentProcessExit`, which Wine 11.19 lacks, and the process aborts. Ziggurat never calls it on Windows: it ends a process tree through its Job Object (section 4).
- std's `rename` on Windows opens the source with write and delete access, and Windows refuses write access to a loaded DLL (`FileBusy`). `MoveFileExW` asks for delete access only and renames a loaded DLL; Ziggurat uses it (section 4). A DLL held open by another process without delete sharing can be neither deleted nor renamed, but Godot can still read and copy it (section 10).
- Under Wine, `std.Io.Dir.access` relative to an open folder never finds a file, while `statFile` does; Ziggurat's existence checks use `statFile`. Wine also replaces `LOCALAPPDATA`, `APPDATA` and `USERPROFILE` with the prefix's own folders.
- A Linux game that Godot's Windows editor exports has no executable bit (Windows has none), so it needs `chmod +x` before it runs.

## 3. Architecture

Five layers; each depends only on layers below it.

```
L5  Editor plugin      menus, build panel, diagnostics, highlighter, templates
L4  Script backend     ScriptLanguage, Script, ScriptInstance, placeholders, loader/saver
L3  Module runtime     loads built modules as generations, gate, reload, state migration
L2  Build service      drives zig, decodes errors, caches, backend policy
L1  Platform services  PathService, DynamicLoader, process spawn, GenerationStore
L0  gdzig              bindings
```

L1 and L2 have no Godot dependency. L4 passes in everything Godot-specific (for example the project root); `globalize_path` is called in L4, never in L1.

**Two binaries in the editor, one in an exported game.**
- **Host** (`ziggurat_host`): built with gdzig, `reloadable = false`, stable. Contains L1 to L5. It owns its GDExtension entry point (gdzig's does not keep `get_proc_address`) and passes it to user modules. `compatibility_minimum` and `compatibility_maximum` are both 4.7.
- **User module**: rebuilt constantly. Contains the user's scripts, a generated root, and the `ziggurat` SDK. Uses gdzig in bindings-only mode (sets `gdzig.raw` from the host's entry data; registers no classes).
- **Game library** (Stage 6, exports only): `libziggurat_game.so` on Linux and `ziggurat_game.dll` on Windows (Stage 7b), the export host and the user module linked statically into one shared library (below and section 10).

**The linked generation** (Stage 6, as built). The export host is the host compiled with the build option `export_build` (no editor classes, no manifest, no message capture, no reload) as a static, position-independent archive per target, `bin/x86_64-linux/libziggurat_host_export.a` (ReleaseSafe, LLVM, stripped, `x86_64-linux-gnu.2.28`). Instead of loading a module with `dlopen`, it declares the module's two exports as `extern` symbols (`ziggurat_describe` and `ziggurat_init`, in `src/host/game.zig`), and at SCENE initialization in a game it calls `runtime.loadLinked`: the same table validation, stamp check and host load checks as `runtime.load`, generation 1, `Generation.lib = null` (the field is optional), `ziggurat_init` once on the main thread, then publish. There is no swap and no reload in an exported game. The game logs `ziggurat: <n> scripts linked`; a refused table logs `Ziggurat refused the module linked into this game: <reason>` and `This game runs without Zig scripts.`, and the game goes on. The export build (section 5) compiles the generated root, the SDK and gdzig in one compiler run, with the archive as a link input, `--force_undefined ziggurat_host_init` (nothing else refers to the entry point, so the archive member would otherwise not be pulled in) and a version script `{ global: ziggurat_host_init; local: *; };`, so the module's two exports resolve inside the library and the library's only exported symbol is the GDExtension entry point. The library imports no `dlopen` (checked after every export build and by the tests). **On Windows** (Stage 7b) the archive is `ziggurat_host_export.lib` (`x86_64-windows-gnu`); in place of the version script the link takes a module-definition file `EXPORTS ziggurat_host_init` (one text, `empty_root.module_definition`), and the generated root marks `ziggurat_describe` and `ziggurat_init` hidden, because the `.def` file alone neither removes a declared export nor the MinGW runtime's exports (section 2). The PE check after every Windows export build accepts exactly one export, `ziggurat_host_init`, and refuses any import of the module loader: a name that starts with `LoadLibrary`, `GetProcAddress`, `LoadPackagedLibrary`, `LoadModule`, and any kernel32 import by ordinal (section 10). The Linux root text and argv are unchanged.

**The registry loader.** In an exported game the `.zig` resource loader answers from the linked table, not from files: `_exists(path)` is true only for script paths in the table, and `_load(path)` returns a script with empty source for such a path without reading a file. An unknown `.zig` path fails with `ERR_FILE_NOT_FOUND` and one error line `Ziggurat: <path> is not part of this export`; when the table was refused, a load fails with `ERR_UNAVAILABLE` and `Ziggurat: <path> cannot be loaded because this export's Zig scripts did not load`. No export string or symbol contains the word `manifest`.

**The only contract between them** is one C-ABI table, returned by `ziggurat_describe`:
- It starts with a magic number, an ABI version and a size field.
- It carries a **layout stamp computed at compile time** from the `@sizeOf` and `@offsetOf` of every boundary struct, the sha256 of the vendored `extension_api.json` and `gdextension_interface.h`, the Zig version, target, float precision and SDK version. A gdzig commit hash cannot be read from a path dependency, so it is not used.
- The host refuses any module whose stamp differs, and refuses to start unless Godot reports exactly 4.7.2 and no `double` feature. At load it reads the table through `ziggurat_describe`, validates it with `ziggurat_abi.validate` and the stamp it computes itself (`ziggurat_abi.expectedStamp`), and only then calls `ziggurat_init(api, gen)` once, on the main thread. The full host contract is the top doc comment of `src/abi/abi.zig`.
- Then the script descriptors (section 8) and the generated wrapper pointers: create, create_blank, destroy, call, get, set, get_default, notification and the optional migrate. **Wrappers take indexes, not names:** method, property and signal indexes are positions in the descriptor arrays (property indexes include group entries). At load the host creates one engine StringName per method, property and signal name, keeps it for the generation's lifetime and maps it to its index; Godot interns StringNames, so a lookup compares the data pointer. The host copies descriptor strings at load instead of borrowing them. `create` refuses a generation other than the one given to `ziggurat_init`.
- **Host load checks.** Two checks the SDK cannot make, because they need the engine's class data, run at load: a script property, method or signal whose Godot name already names a property, method or signal of its `extends` class or an ancestor (it would hide the engine member, for example `pub fn draw` on a Node2D; virtual methods such as `_ready` override on purpose and are not checked), and an exported Node-typed field in a script whose `extends` is not a Node (only exported fields are described with their type). Each finding is a diagnostic on the script (no line), and the build counts as failed: the generation gets no new instances and the manifest is not written.
- **ABI version 2** (Stage 4) gives the host what it needs to migrate instances and to read defaults without running module code. Each script lists every field of its instance struct (`base` and private fields included) as a `FieldDesc`: name; Zig type name (`@typeName`, with Zig's anonymous-type counters removed, because the counter depends on what the compiler analysed first); `shape`, a hash of the inner layout for struct, array, union (with tag values), enum and packed types and 0 for types whose name fixes their layout; offset, size and alignment; a **value kind** that tells the host how to read the bytes (bool, signed or unsigned integer, float, `f32` or `i32` vectors, color, empty text, null object, signed or unsigned enum, flags, none, other); and `bits`, the logical width of integer, enum and flags values, so the host masks unused bits instead of trusting how the compiler filled them. **Exact type identity** is equal type name, shape, size and alignment. The table no longer carries a layout hash: the host computes it (`ziggurat_abi.layoutHash`) from the instance size and alignment and each field's name, type name, shape and offset, which also removed the most expensive comptime hashing from the SDK. `create_blank(owner, gen)` makes an instance at its defaults with `base` set and does not run `init`; `migrate(new, prev)` is the script's optional hook, and `PrevView` is the old instance as the hook sees it (data, field list and one `moved` byte per old field: 0 untouched, 1 moved, 2 read). The validator also checks that each field's size fits its value kind, that offsets are multiples of the alignment and that no field is more aligned than the instance. The full contract is the top doc comment of `src/abi/abi.zig`.

**Boundary rules.**
- Engine objects cross as raw object pointers or ObjectIDs, never as copies of wrapper types. Only the host registers ClassDB classes.
- **The SDK is a curated surface, not a re-export of gdzig.** It exposes engine classes (flat, with Godot's own spellings: `z.godot.Node`), builtin value types, and our own checked helpers, and withholds `Registry`, `ClassDb.register*`, `GDExtension`, `GDExtensionManager`, Callable constructors from raw function pointers, and gdzig's `Variant` helpers. `z.godot.Callable` is an SDK type that builds only (object, method name) Callables, which always resolve to the current generation; there is no `fromClosure`. `z.godot.ClassDB` is a read-only SDK forwarder (`classExists`, `getParentClass`, `isParentClass`, `classHasMethod`, `canInstantiate`, `instantiate`).
- The SDK owns a **checked conversion layer** (below). User code and wrappers never call gdzig's Variant conversions directly.
- L4 talks to gdzig through its own thin wrapper layer, so gdzig API changes stay contained.

**Checked conversion layer (SDK).**
- Follows Godot's strict conversion rules (int and float, String and StringName, nil to null object). Integer narrowing is range-checked; an engine enum value outside the known tags is refused with `CALL_ERROR_INVALID_ARGUMENT`, never converted with an unchecked `@enumFromInt`; every failure returns Godot's call-error code and never panics.
- Objects are resolved only through ObjectID (`objectGetInstanceFromId`), then checked with `is_class` against Godot's exact class name (gdzig derives wrong names for 242 classes, section 13); a failed check is `CALL_ERROR_INVALID_ARGUMENT`.
- `Ref(T)` is an owning RefCounted handle with Godot's first-reference semantics. `Ref.adopt(p)` takes over a reference the caller already holds (a fresh `T.init()`, or a RefCounted that an engine method returned); `Ref.set(p)` adds one.
- **Ownership at the boundary.** Arguments are borrowed for the length of the call. Plain return values are borrowed: the wrapper copies them into the result and never releases them. A newly made String, StringName, NodePath or `Ref` is returned as `z.Owned(T)`, which the wrapper releases after the copy. `z.assign(dst, src)` stores a borrowed value (takes its own reference or copy, releases the old value). Exported text fields use owning types (section 8), so storing a borrowed argument with `=` does not compile.
- Comptime names are a separate type without `deinit` (never free static StringNames).
- Lazy caches are warmed on the main thread at module init (`ziggurat_init` warms the SDK's own binds and every class name and signal name the descriptors use). Until Stage 7a a lazy cache the descriptors do not show (a class check on a private field or a local, a `Callable` method name) had to be used on the main thread first. Since Stage 7a the lazy caches are safe under threads on every CPU (gdzig patch 5 and the SDK, section 13). A flag-and-value cache (`StaticName`, `MethodBind`, gdzig's `fromComptimeLatin1`) has three states (empty, filling, ready): a thread builds its value in a local, the one that wins a compare-and-swap from empty to filling stores it and then publishes ready with a release store, and readers load the state with acquire. A losing `StaticName` waits (a short spin, no Godot call inside) for the winner's 8-byte store, because it must return a pointer to the stored name; a losing `MethodBind` returns its own lookup. A loser's copy is never freed (one extra static reference, never a double free). gdzig's single-pointer caches use an acquire load and a release store on the pointer. The main-thread warm-up stays.

**Ownership rules.** Engine-heap values may be freed by any copy. Zig-heap memory is freed only by the generation that allocated it. Instance memory comes from a host-provided allocator, so generation N+1 never frees memory that generation N's allocator allocated.

## 4. L1: platform services

Every path, library load and process spawn goes through these. No other code builds a path string or calls `dlopen`.

```zig
pub const OsPath = struct { bytes: []const u8 }; // WTF-8; built only through join()
pub const PathService = struct {
    pub fn init(roots: ProjectRoots) PathService;           // roots injected by L4
    pub fn dir(self: PathService, kind: DirKind, a: Allocator) !OsPath; // cache, config, temp, toolchain
    pub fn join(a: Allocator, base: OsPath, parts: []const []const u8) !OsPath;
    pub fn libName(t: std.Target, stem: []const u8, gen: u32) []const u8; // unique per generation
    pub fn importLiteral(a: Allocator, rel: OsPath) ![]const u8;          // forward slashes, escaped
};
pub const Loader = switch (builtin.os.tag) {
    .windows => @import("loader_windows.zig"),
    else => @import("loader_posix.zig"), // Linux; macOS in Stage 7c
}; // each: open(OsPath) LoadError!Library; lookup(Library, comptime T, [:0]const u8) ?T;
   //       close(Library) void; describeError(buf) []const u8
pub const GenerationStore = struct { stage(built, extras) !Staged; pin(gen) Lock; sweep() void };
// Staged = { gen: Generation, pin: Lock }: the new generation comes back pinned
```

- **Per-OS directories.** Linux uses XDG; Windows `%LOCALAPPDATA%\ziggurat\cache` (cache and temporary files) and `%LOCALAPPDATA%\ziggurat\toolchains` (the downloaded Zig), and `%APPDATA%\ziggurat` for configuration; macOS `~/Library/Caches`.
- **Target keys** (Stage 7b, `src/platform/target_key.zig`, std only): `x86_64-linux`, `x86_64-windows`, `aarch64-macos` and `x86_64-macos`. They name the folders under `addons/ziggurat/bin/`, `addons/ziggurat/sdk/` and `.godot/ziggurat/export/`. `fromTarget` maps a Zig target and `fromFeatures` Godot's export features (`linux` + `x86_64`, `windows` + `x86_64`) to a key; `files(key)` gives each target's library names (null for macOS until Stage 7c). The package holds `x86_64-linux` and `x86_64-windows`.
- **Linux loader.** `dlopen` with `RTLD_NOW | RTLD_LOCAL`. **Windows loader** (Stage 7b, `loader_windows.zig`). It first reads the DLL and runs the PE completeness check (`pe.checkComplete`, below). Then `LoadLibraryExW(path, null, LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | LOAD_LIBRARY_SEARCH_DEFAULT_DIRS)`: the full path comes from `GetFullPathNameW`, and a path of 260 characters or more gets the `\\?\` prefix. Symbols come from `GetProcAddress`, unloading is `FreeLibrary`, and errors are `FormatMessageW` text in the loader's error sentence. **macOS loader.** `dlopen` through the POSIX loader; not run (Stage 7c).
- **Locks** (Stage 7b). On Windows, file locks use kernel32 `LockFileEx` and `UnlockFileEx` on the whole file (shared or exclusive; `LOCKFILE_FAIL_IMMEDIATELY` for a try-lock; `ERROR_LOCK_VIOLATION` means held by someone else, and any other error is logged with its Windows error code). std's `tryLock` fails under Wine (section 2). Linux and macOS keep `flock` through std.
- **Process control** (Stage 7b, `src/platform/process.zig`). On Windows the compiler child starts suspended, is assigned to a new Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and only then resumes, so no process it starts can escape the job. The exit wait is `WaitForSingleObject` with the existing deadline; a timeout, an output over the cap or `Session.interrupt` terminates the job, which ends the whole tree. After a normal exit the job handle closes, so processes the child left running end too (on Linux nothing kills them; the one difference). std's `Child.kill` is never called on Windows (section 2).
- **File identity** (Stage 7b). `safe_open.identity` on Windows is `GetFileInformationByHandle`: the volume serial number, the 64-bit file index, the size and the last-write time. The manifest re-check (section 6) uses it as it uses device and inode on Linux.
- **`--import` and `--quit` detection** reads `/proc/self/cmdline` on Linux and `GetCommandLineW` with `CommandLineToArgvW` (SHELL32) on Windows.
- **Renaming a loaded DLL** (Stage 7b). `platform.moveFile` is `MoveFileExW(from, to, 0)` with full paths and `\\?\` for long paths; std's rename cannot rename a loaded DLL (section 2).
- **Imports of the Windows editor DLL.** Only kernel32, ntdll, SHELL32 (`CommandLineToArgvW`) and the Universal C Runtime (`api-ms-win-crt-*`); no MSVC runtime. The editor DLL imports the module loader on purpose; the game DLL must not (section 3).
- **Hidden Linux assumptions to avoid.** `lib*.so` names (use `libName`), copying a loaded file, backslashes and quotes in generated `@import` strings, case-insensitive file systems (the build checks that script paths do not differ only by case), spaces and unicode in paths, read-only project folders, two editors sharing one cache folder (a lock file per cache entry).
- **GenerationStore** stages each build into its own folder, takes a lock file per generation, sweeps stale generations at editor start, and keeps those a running game still uses. A cap on count and total size applies. Generations were about 15 to 25 MB each with the Stage 0 spike SDK; with the real SDK one generation measured 109 MB on disk (397 MB apparent) at 300 scripts and 341 to 357 MB on disk (1.29 GB apparent) at 1000 (Stage 3). Incremental outputs are sparse files about 2.7 times the non-incremental size, so staging copies keep the holes. Since Stage 4 the store measures generations by allocated blocks (`statx` block counts on Linux), so the caps count what the disk holds; Windows and macOS still count apparent sizes (Stage 7b did not measure allocated sizes on Windows; risk 37). **On Windows** (Stage 7b) the store runs the PE completeness check on each staged library, and a generation folder the sweep cannot delete (a loaded DLL, access denied, a sharing violation) is renamed into `<store>/.trash/<gen>-<16 hex>` (if the folder rename fails, its files are renamed one by one into such a folder). It counts as deleted. Each sweep first deletes what it can from `.trash/`: only entries in exactly that name form, never through a linked `.trash` (a symbolic link or junction is left alone). A pinned generation is never renamed. This rename-then-delete is what lets a session's disk be reclaimed after the DLLs are unloaded at editor exit. **Caps and pins** (Stage 5): `max_count` (default 8) counts every generation, pinned or not; `max_bytes` (default 1 GiB) counts only the bytes of unpinned generations; a pinned generation is never deleted. `stage` returns the new generation already pinned (a shared lock on its `.lock`, taken under the exclusive store lock), so no sweep can delete a build between staging and the moment the editor loads it or drops it (section 6). Because `max_count` still counts pinned generations, a tool-script session with many loaded builds keeps fewer old unpinned builds than `max_count` suggests.
- **Zig locator.** In order (Stage 5): the project setting `ziggurat/zig_path` (a per-project override, empty by default), the editor setting `ziggurat/zig_path` (per user, in Editor Settings, with a file picker), the Zig that Ziggurat downloaded (`<toolchains>/zig-0.17.0`, section 9), then `PATH`. The editor reads both settings again at every build request, so a downloaded Zig or a changed path works without a restart. A relative path in the setting that applies (the project setting, or the editor setting while the project setting is empty) builds nothing: the request gives a failed build at once, whose message names the setting. The version is checked; Ziggurat needs exactly the pinned Zig version, because Zig changes its language and standard library between releases. A wrong or missing Zig gives one message that names the needed version and ends `Set the editor setting ziggurat/zig_path to a Zig 0.17.0 executable.`; the build outcome also carries the kind of problem (`ZigProblem`: none, missing, wrong version, no answer), so the editor offers the download without parsing text (section 9). Since Stage 6 the build service scans the project before it looks for Zig, so a project without Zig scripts needs no Zig at all (section 5).
- **Export pins** (Stage 6, `src/platform/pins.zig`): `export_glibc = "2.28"`, the highest `GLIBC_` symbol version the official 4.7.2 `linux_release.x86_64` and `linux_debug.x86_64` templates need, and `export_target = "x86_64-linux-gnu.2.28"` with the baseline CPU (no `-mcpu`). The export host archive, the empty game library, the packaged editor library and every export build use this target, so exported games and the shipped editor library run on any Linux with glibc 2.28 or newer. The Windows counterparts (Stage 7b) use `x86_64-windows-gnu` with the baseline CPU.
- **ELF symbol reader** (Stage 6, `src/platform/elf.zig`, std only): `dynamicSymbols` and `neededVersions` read a library's dynamic symbols and needed `GLIBC_` versions from memory, with every offset, size, count and link range-checked (a malformed file gives an error, never a loop or a read out of bounds). The export build checks its output with them, and the tests use them in place of `nm` and `readelf`.
- **PE reader** (Stage 7b, `src/platform/pe.zig`, std only). `checkComplete(bytes)` checks the DOS and PE headers and that every section's raw data lies inside the file, with checked arithmetic; it is the PE version of the ELF completeness check, used by the loader and by the store after staging. `exports` and `imports` list a DLL's exported names and its imports (DLL and function; ordinals named `#<n>`; delay-load imports included). Every read is bounds-checked; more than 96 sections is a bad header, and each list has a budget (65,536 names, 4,096 bytes per name, 16 MiB per list, else `error.TooLarge`), so a hostile file cannot make it use memory or time out of proportion. A malformed-input fuzz test runs natively and under Wine.

## 5. L2: build service

- **Where the generated root lives.** A Zig module can import only files below its root file's folder, so the root cannot sit in the cache or in a subfolder. The build writes one hidden generated root file, `<project>/.ziggurat_root.zig`, that imports every script with one top-level `const` per script. Godot's file scan skips dot-files, so the root is not in the filesystem cache and gets no `.uid` (verified, Stage 0 spike s1-root). A cache-side build file imports it as module `project`. The script folders default to `res://`; the generator itself skips folders with `.gdignore` and `addons/`, because Godot's scan does not skip `addons/`. All builds run from one cache folder: Zig rebuilds its build runner for each new build folder.
- **Read-only projects.** When a probe write at the project root fails, the build writes the root and a mirror copy of the `.zig` files into `<cache>/mirror-<project id>/` and builds there. Error paths are mapped back by replacing the mirror prefix; Zig reports them relative to the build folder, so the mapping handles relative and absolute paths. The mirror is re-synced on every build. A symlink farm also works on Linux, but it needs symlink rights on Windows.
- **The generated root owns the C exports.** `ziggurat_init` and `ziggurat_describe` are non-generic functions declared in the generated root, which refers to each script's compile-time descriptor table; the SDK provides non-generic init code and emits no exports. An export from a generic SDK function instantiated per script type went stale under incremental compilation after a field change, with 0 errors (Stage 0 spike s2-warmup; section 13). As a second check, after each update the build service compares the output's table with what it expects, because a swap that silently keeps old code is worse than a failed build. Three checks exist since Stage 4: the table must carry this build's id; a script whose layout hash changed although its file did not (and no helper changed) makes the service rebuild in full, with the message "layout of <script> changed although its file did not; rebuilding in full"; and after each build the editor loads, the host compares every property's `get_default` (module code) with the default the table snapshot decoded from the defaults image by `FieldDesc` offsets (host code, no module code run). A mismatch rejects the build (it stays loaded but is never swapped to) and, for an incremental build, requests a full rebuild (`BuildService.requestFull`); on a full build it is only an error, so no rebuild loop starts. This check was added for the miscompile in section 2; its limits are in section 14. The root keeps the per-build id out of the checked script list (`scriptList` checks and copies the descriptors, `tableOf` adds the id), so a body edit does not re-run the whole-table check over every script (section 12). In an export build the root's two exports stay inside the game library: a version script keeps them local, and the export host reaches them as `extern` symbols (section 3).
- **Which files are scripts.** A file with a top-level `pub const extends`. Other `.zig` files compile as helpers inside the same module. Helpers that fail to compile standalone, `test` blocks, and same basenames in different folders were tested and are fine.
- **One module for all scripts**, as verified: a file cannot be in two modules, type identity would split, and each module carries its own 10 to 15 MB of std and gdzig. Body edits stayed at 20 to 26 ms with 300 scripts (earlier research; Stage 0 measured 39 ms median, 131 ms first edit; Stage 3 with the real SDK 131 ms median after the root table fix, 514 ms before it; Stage 4 127 ms, section 12). To avoid replacing every script on each swap, the host computes a **layout hash per script** from its field list (section 3); if it is unchanged, only function pointers swap and the instance data stays.
- **One declaration per script.** The root describes each script in its own top-level `const`. Describing 300 scripts in one comptime block exceeded the branch limit.
- **Optional extras.** `ziggurat.zon` lists extra package dependencies, merged into the generated build. Users do not own `build.zig` in v1.
- **Driving the compiler.** The compiler server (`--listen`) returns an `ErrorBundle`. Errors from SDK code carry the script's path in their message; the host maps them to a line with a text scan, so the script editor shows a line for these too. Any other error outside the project's files whose reference trace names a project file is reported at the first such frame (the compiler keeps two frames by default; editor builds ask for 16 since Stage 7a, below), for example the error of a withheld gdzig helper (section 13). `_validate` only reads cached diagnostics; it never compiles. A `--listen` session refuses `-femit-bin`, so the service finds the output through the `emit_digest` message and copies it out after each clean update.
- **Triggers** (as built in Stage 5). Each successful save of a `.zig` file through the saver (`save`); Play (`EditorPlugin._build`, `play`, section 9); the Zig panel's Build button and Tools > Build Zig Scripts (`manual`), also asked for by the editor after a Zig download installed; a change check at editor focus-in, optionally on an interval, and every 2 s while a game from the editor runs (`watcher`, below); and the **build at project open** (`open`): at once when the project setting `ziggurat/zig_path` is set, otherwise when the editor plugin enters the tree (`_enter_tree`; the editor setting can be read only once the editor exists), with the first frame as the fallback. Builds run off the main thread, one at a time; triggers during a build merge into one follow-up build.
- **Files changed outside the editor** (Stage 5). There is no OS file watcher. `BuildService.requestIfChanged` asks for a build that the build thread runs only when the scan differs from the last build's: the scan id covers the path, size, modification time, change time and inode of every script and helper file. Without a difference it builds nothing and publishes no outcome; a request already pending is built as usual. The editor plugin calls it when the editor regains focus (`NOTIFICATION_APPLICATION_FOCUS_IN`) and, while the editor setting `ziggurat/build/check_interval_seconds` is above 0 (default 0), at that interval. While that setting is 0 and a game started from the editor runs (a debugger session of the plugin is active; Stage 7a), it calls it every 2 s (`running_check_ms`), so an edit made outside Godot reaches the running game without focusing the editor; the check starts and stops with the session, and a non-zero interval always wins. The plugin asks Godot for its sessions at each 2 s tick instead of tracking start and stop. A check that finds nothing costs about 21 ms at 1000 scripts on the build thread (section 2); the main thread only sets a flag. Because the id includes the change time and inode, a `chmod` or `touch` builds once; a false positive costs one build, a false negative would miss an edit. Two writes of the same size to the same file within one file-system timestamp tick look unchanged. There is no OS watcher (inotify and its Windows and macOS counterparts differ); Stage 7a chose the check while a game runs instead.
- **Backend policy** (table keyed by target, `src/build/backend.zig`; since Stage 7a two editor settings change it, below):

| Platform | Default | Reload latency | Status |
|---|---|---|---|
| x86_64 Linux, session start | LLVM or self-hosted non-incremental | seconds | measured (5.4 s for 300 scripts; 6.4 s in Stage 0; 26.3 s with the real SDK in Stage 3; 12.0 s at 300 and 42.7 s at 1000 in Stage 4) |
| x86_64 Linux, after warm-up | self-hosted + incremental | Stage 0: 20 to 94 ms body edit (median), first edit up to 275 ms; real SDK (Stage 3, after the table fix): 131 ms at 300 scripts, 428 ms at 1000 (514 and 1684 ms before it); Stage 4: 127 ms and 512 ms | measured (section 12); warm-up 3 s to 86 s by project size and shape, 65 s and 216 s with the Stage 3 SDK, 28 s and 93 s in Stage 4 |

| aarch64 Linux | LLVM, non-incremental | seconds | Zig 0.17's self-hosted aarch64 backend fails on trivial code (section 2); recheck with the next Zig |

| macOS | LLVM | seconds | incremental panics |

Every editor session starts with a non-incremental build and warms the incremental compiler server in the background; the incremental path is an optimization on a correct slow path, never a requirement.

**Debugger builds and the backend setting** (Stage 7a). Two editor (per-user) settings, read at every build request:
- `ziggurat/build/debugger_builds` (bool, default false). While it is true, every build uses the debugger-build row (`policy(.debug_build)`: LLVM, non-incremental, Debug), no incremental update runs and no warm server starts, so lldb can read every build. The Zig panel shows `Debugger builds: on (slower, no incremental)`.
- `ziggurat/build/backend` (`auto`, the default and the table; `llvm`; `self_hosted`; `self_hosted_incremental`). It overrides the table for the session-start and warm phases only, never for debugger builds, and `debugger_builds` wins over it. A value outside the list reads as `auto`, with one warning per session: `Ziggurat: the editor setting ziggurat/build/backend has an unknown value; using auto.` A value the target cannot build (`self_hosted` on aarch64 Linux) gives the compiler's own error, not one that names the setting. It is a way out when incremental mode misbehaves (risk 8) and a way to try self-hosted builds on new targets.

A change of either setting applies at the next build (`BuildService.setPolicy`, no service restart): the build thread stops the warm server first (it marks the warm-up abandoned, interrupts an update that runs, joins the warm thread and only then drops the server), and a warm-up killed this way does not count as a server death. The build at project open can run before the editor exists and cannot read editor settings then; when either setting is not at its default, the editor requests the open build once more when it is ready.
- **Script naming rules.** Zig `camelCase` maps to Godot `snake_case`; the mapping copies Godot 4.7.2's own `String::to_snake_case` (`_separate_compound_words`, `core/string/ustring.cpp`) exactly: a break goes before an uppercase letter that follows a lowercase letter, before the last capital of an uppercase run when a lowercase letter follows (`HTTPUrl` gives `http_url`), and at letter/digit boundaries (`vec2` gives `vec_2`). A capital run stays one word, so `getHealthHUD` gives `get_health_hud`. The mapping loses information, so two names that map to the same Godot name are a compile error. Because the digit rule differs from Godot's hand-written names (`vector2`), a script can set the Godot name explicitly with a name override in its metadata. A leading `_` means "private" for fields but "Godot virtual" for functions.
- **Panic handling.** The generated root installs a panic handler that logs to Godot and then aborts. Recovery is impossible by nature; the design makes it visible, not survivable. Editor builds use Debug or ReleaseSafe, because ReleaseFast silently returns garbage on out-of-bounds access. In the editor, a panic only occurs through tool scripts; non-tool scripts run in the separate game process.
- **Debugging** (Stage 7a). Debugger builds (above) make every editor build readable by lldb; `--export-debug` keeps debug information in the game library (section 10). The add-on's README has a "Debugging with lldb" section: the setting, `ptrace_scope` 1, breakpoints by `file:line`, running the game under lldb from a terminal (tested: a host test stops at a script line and reads `self`), and starting the game through `lldb-server` with Main Run Args (not tested).
- **Reference trace** (Stage 7a). Every editor build, full and incremental, passes `-freference-trace=16`, so an error inside other code (such as a withheld gdzig helper) is mapped to a script line up to 16 frames deep (risk 24). It costs +0.4 % on the median body edit at 300 scripts (section 2). Export builds do not pass it.
- **Projects without scripts** (Stage 6). The build thread scans the project before it looks for Zig. Without scripts the outcome is a good build with no generation (`ok`, no generation, no snapshot, no Zig problem, only the scan's problems as diagnostics): no root is written, no Zig is located and no compiler runs. The editor logs `ziggurat: no Zig scripts; nothing to build (<trigger>, <ms> ms)`, the panel shows `No Zig scripts; nothing to build`, and Build on Play returns true, so a GDScript-only project with the add-on plays without Zig. A project with only helper files (no script) builds nothing either, so a helper's compile error shows once a script imports it. When every script is deleted after a good build, the last generation stays loaded and named in the manifest until the editor exits (harmless; no script uses it).
- **The export build** (Stage 6, `src/build/export_build.zig`, `export_build.run`, blocking, any thread). It scans the project, prepares the editor's own workspace (`<cache>/projects/<project id>/`, so an export build and an editor build of one project take turns on `build.lock`), writes the generated root with the fixed build id `export` (scripts sorted by path, as always), and runs one non-incremental compiler process through the compiler server with the Zig the caller located: `zig build-lib -dynamic -lc -fllvm --name ziggurat_game`, the export host archive, `--version-script` and `--force_undefined ziggurat_host_init` (section 3), and for the root and every SDK module `-target x86_64-linux-gnu.2.28 -OReleaseSafe -fstrip` (`-fno-strip` for a debug export since Stage 7a, section 10). A Windows export (Stage 7b) builds `ziggurat_game.dll` with `-target x86_64-windows-gnu`, the archive `ziggurat_host_export.lib`, the module-definition file in place of `--version-script`, and the generated root with hidden exports (section 3); the compiler's output name follows `-target`, not the editor's OS, so either editor can export either target. A release export build is deterministic (a debug export is not, risk 34; for Windows exports the two-folder test does not run, only Linux is tested): the same project in two folders (one with spaces and non-ASCII names) gives the same bytes, and the library holds no project, SDK, cache or Nix store path. It has no debug information because debug information held absolute paths (section 2); exported games therefore print panics and stack traces without symbol names. Compile errors are decoded and mapped to project files exactly as in editor builds. Since Stage 7a a scan problem fails the export build: right after its scan, before the workspace and the compiler, `run` returns `ok = false` with the problems as diagnostics (editor builds still only report them). A clean output is checked before it is written (only `ziggurat_host_init` exported, no `dlopen` import, no `GLIBC_` version above 2.28; on Windows the PE check of section 3) and then copied atomically (a temporary file renamed over the target) to the output path; a failed build or check never touches the output path. The root is written into the project folder (the editor's next build writes its own root back, so a warm incremental server compiles the root once more), or into the mirror for a read-only project. The export waits up to 120 s for an editor build that holds `build.lock`. Cold, a two-script project built in about 8 s in Task 1's prototype (the SDK and gdzig in ReleaseSafe with LLVM) and 3.5 s in the install test; larger projects are not measured (risk 25).
- **The SDK the editor builds against** (Stage 6). The add-on ships the SDK as source in `addons/ziggurat/sdk/` (section 1), staged by `tools/sdk_stage.zig` (`zig build sdk-stage -Dsdk-out=<absolute folder>`; `zig build host` and `zig build package` use the same cached stage). The folder holds `.gdignore` (so Godot neither imports it nor exports it, and the script scan skips `addons/` anyway), `sdk-manifest.json` (Zig version, SDK version and the modules with their dependencies) and one folder per module with the module root and every file that root reaches through a relative `@import` or `@embedFile` (found with `std.zig.Tokenizer`, not by copying folders). There are 11 modules: `ziggurat`, `gdzig`, `ziggurat_godot`, `sdk_options`, `ziggurat_abi`, `build_options`, `casez`, `gdextension` (the translate-c output), `common`, `c_builtins` and `helpers`. In gdzig every line that holds only a `///` doc comment is removed (about 76 MB of Godot's documentation text; `//!` lines stay), and in the translate-c output every comment-only line (they named Nix store header paths); each stripped file is parsed again and the stage stops on a parse error. Stripping shifts line numbers in those files, so an error inside gdzig names a line of the shipped copy. The staged SDK is about 161 MB in 1143 files per target (Stage 7a; 132 MB before gdzig patch 5). The manifest's module roots are **relative to the manifest's folder** (`gdzig/gdzig.zig`); `sdk_manifest.load` resolves them against the folder and refuses a root that leaves it (a text check, so a symbolic link inside the folder is followed) or that names a folder. The stage is made for one target, and the translate-c output differs per target, so **the SDK is per target** (Stage 7b): the package holds `sdk/x86_64-linux/` (staged for the export target `x86_64-linux-gnu.2.28`) and `sdk/x86_64-windows/`. The editor uses its own target's `res://addons/ziggurat/sdk/<target key>/sdk-manifest.json` (globalized) when the project setting `ziggurat/dev/sdk_manifest` is empty; the setting stays as a developer override, must be absolute, and overrides only the editor's own target. An export uses the SDK of the target it exports to (`editor_build.exportInputs`), so a Linux editor exports Windows with `sdk/x86_64-windows/` and the other way round. Without an SDK, the editor starts no build service and logs one sentence that names the shipped path (a missing manifest and an unreadable one give different sentences). An add-on installed before Stage 7b has its SDK directly in `sdk/`; a hand-set `ziggurat/dev/sdk_manifest` that still points at that old `sdk/sdk-manifest.json` keeps the old SDK in use (the README says to delete the old add-on folder first).

## 6. L3: module runtime and reload

A **generation** is one successfully built, validated module, staged in its own folder by `GenerationStore`.

**The gate** (as built in Stage 4, `src/host/gate.zig`). Every entry from Godot into module code, or into an instance record a swap rewrites, holds the shared side of one process-wide reader-writer lock: the instance callbacks that read the record or run module code (`set`, `get`, `get_property_state`, the property and method lists, `has_method`, revert, property type, argument count, `call`, `notification`, `to_string`, `free`), `_instance_create` from before it picks the generation until the new record is registered (so a swap never misses an instance made meanwhile, and an instance made on another thread during a swap lands on the new generation), and the placeholder updates that read descriptors. Callables and signals reach module code only through `call`. Not gated: callbacks that read neither the record's generation nor module data (`get_owner`, `get_script`, `is_placeholder`, `get_language`, the list frees) and the refcount callbacks, which do not reach the module. Rules:
- A swap takes the write side only with a **try-lock**, never a blocking lock; if it fails, the swap retries next frame. In Zig 0.17 a blocking writer would make every new reader wait, including a thread that is already inside and calls into another instance, which would then wait for itself.
- A per-thread **depth** counts entries. The swap runs from `_frame` only when the main thread's depth is 0. A nested `Main::iteration()` while a script's own frame is on the stack therefore defers the swap (`deferred_depth`), and a nested `_frame` runs neither the main-thread queue nor a swap. Build on Play's own queue run follows the same rule (section 9).
- `reload()`, `_reload_scripts`, `_reload_all_scripts` and `_reload_tool_script` only queue work; they never swap.
- **Callbacks during migration** (closes the Stage 3 open item): the thread that holds the write side passes through the gate, so `migrate` and the old `deinit` may call into instances. A call into the one instance being migrated is refused (`CALL_ERROR_INSTANCE_IS_NULL`, which Godot reports as an invalid method for `Object.call`; `get` and `set` fail, `get_property_state` reports no properties, `to_string` falls back to Godot's default text, and a `notification` is dropped, for example one that a child freed in `deinit` sends to the owner), with one log line per instance and swap. Instances not migrated yet run old code; migrated ones run new code. An instance such code frees is taken off the registry and released after the swap; one it makes lands on the new generation. `migrate` and an old `deinit` must not wait for another thread, or for a lock another thread may hold while it calls a Zig script (a GDScript `Mutex`, `Thread.wait_to_finish`, a `ResourceLoader` load whose loader thread makes Zig instances): during the swap every other thread that enters the gate waits there, so such a wait never ends and the editor or game hangs. The host's own code never waits like this; user code must not either.
- Godot calls that can take Godot's own locks (placeholder refresh, the Inspector's `property_list_changed`) run only after the write side is released, because a thread waiting at the gate may hold such a lock.
- Shutdown waits for the write side by retrying the try-lock after the main loop stopped (about 5 s at most, then it continues), so a nested entry on another thread can still get in and leave.
- Each instance record carries a serial number, so a record whose address is reused during a swap is not mistaken for the old one. Calls on one instance from two threads at once are not serialised; the script must guard its own data.

**Reload sequence** (swap steps run from `_frame` under the gate):
1. Build produces a new module and descriptors (off the main thread).
2. Check that the staged copy is a complete ELF file (section headers and `PT_LOAD` segments inside the file, every offset sum done with checked arithmetic; on Windows a complete PE file, section 4), then load the new generation next to the old one (`RTLD_LOCAL`, unique path). `dlopen` accepts a library whose tail is cut. The check is size consistency, not integrity; a content hash written by the build would close that gap.
3. Validate magic, ABI version, layout stamp and the descriptor table, then run the host load checks (section 3) and, in the editor, the defaults check (section 5). On any failure, keep the old generation and report the error. Nothing has changed yet. A swap request (`swap.request`; the request with the highest generation number wins, and one older than the current generation is dropped) targets the latest generation that loaded and passed every check, never a rejected one.
4. At `_frame`, under the write side of the gate, plan per script: an equal layout hash, instance size and alignment keeps the instance data; a changed layout moves the fields whose **name and exact type identity** match (section 3; `base` never moves). A script the new generation lacks keeps its instances on the old code.
5. Allocate: `create_blank` a new block for every instance whose layout changed. **This is the rollback boundary.** Loading, validation, the load checks and every allocation happen before it; any failure frees every new block (with `HostApi.free`: a blank block holds only the defaults, which hold no engine value, so no module code runs) and keeps the old generation. Migration itself cannot fail; a user panic aborts, as everywhere.
6. Migrate per instance, as a **move**. Same layout: move the data block's tag to the new generation (`runtime.retag`) and rewrite the record's generation and descriptor index. Changed layout: mark the instance as migrating; byte-copy every matching field and mark it moved; call the new generation's optional `migrate(new, old)` (its `take` moves more fields, its `get` marks fields read); reset every field marked moved in the old instance from the old defaults image; call the old `destroy`, whose `deinit` releases only what did not move, such as engine references held in old state; then write the record's generation, index and data as one unit, with no module code between those writes. `init` never runs again, because a copied pointer set in `_ready` must stay valid. Without the reset, owned memory moved to the new generation would be freed by the old `deinit`.
7. Publish the new generation as current and release the write side. Then free the records released during the swap, log dropped fields and missing scripts (a removed or retyped field that `migrate` did not take or read; once per script path and pair of layouts, so swaps back and forth stay quiet), refresh every placeholder and tool placeholder (`_update_exports`), and in the editor send `property_list_changed` for each object whose instance moved to a changed layout. Script answers read `runtime.current()`, so descriptors need no refresh.

Tested in Stage 4: same-layout and changed-layout swaps, owned fields moved, taken and dropped, rollback after a failed allocation, three threads calling methods during 20 changed-layout swaps (about 1.5 million calls each, 0 errors), and `zig build test-stress` (section 11).

**Accounting.** Live bytes per generation count only the instance data the host allocated for that generation. The user heap behind `z.allocator` is shared by all generations. A same-layout swap moves the data block's tag to the new generation with the host-internal `runtime.retag`; no ABI change was needed.

**While code is broken** the last good generation keeps running, placeholders stay on with fallback enabled, and the last good descriptors feed the Inspector.

**Where descriptors live.** In the project, at `.godot/ziggurat/descriptors.json`, not in the per-user cache, so a restarted editor or a fresh machine still has them after the first build. The editor writes it after each good build (temporary file, rename, folder `fsync`), from the loaded generation or, when it loads none, from the table snapshot, and reads it at startup, so the Inspector and placeholders work before the first build finishes; once a build's descriptors exist in the session, the file no longer answers. Property defaults are stored as typed JSON per v1 type (numbers, `"nan"`, `"inf"` and `"-inf"` for floats, strings for String, StringName and NodePath, flat number arrays of the exact component count for vectors and matrices, integers for enums and flags, `null` for object handles) and rebuilt as a Variant of the property's declared type; anything else is ignored with one log line. Godot's `str_to_var` is never used on the file: it can construct objects from text and overflowed the stack on deep nesting. When a script has no descriptors, `_is_valid` is false and `_is_placeholder_fallback_enabled` is true, so scene values survive saving; signal connections survive as described in section 2. A build runs at project open.

**Unload policy.** Old generations are not unloaded in v1; old code can still be reached through Callables and similar. This is safe to rely on because: only (object, method) Callables are allowed, and they resolve to the current generation; native threads and `WorkerThreadPool` tasks from user code are forbidden in v1; and old instance memory is released by `deinit` at migration. Each reload costs one generation on disk and in the address space: in Stage 4, 106 MB allocated (326 MB apparent) at 300 scripts and 349 MB allocated (1.41 GB apparent) at 1000 for an incremental build (Stage 3: 109 MB and 341 to 357 MB; at 300 scripts about 100 MB of the 397 MB apparent size was debug information), plus 256 KiB of thread-local storage per thread that touched the module. In the 300-edit stress run (five small scripts, 289 loaded generations) the editor's resident memory grew from about 800 MiB early in the edit loop to about 970 MiB at the end, about 0.7 MiB per loaded generation (section 14). The editor pins every generation it loads until it exits, and the game pins every generation it loaded (one lock file, and so one file descriptor, per generation until exit). On Linux a deleted file that a process still maps frees nothing until that process exits, so no sweep can reclaim space within one editor session. On Windows a loaded DLL cannot be deleted at all; the sweep renames its folder into `.trash/`, and a later sweep deletes it once no process holds it (section 4).

**Editor generation policy** (Stage 4). The editor loads a build only when its code is needed: when the project has at least one tool script, or while a live tool instance still exists (when the last tool script goes away, this is logged once). Otherwise the build service's **table snapshot** feeds the descriptors, the placeholders and the descriptor cache. The service takes the snapshot while the library is open for its table check: pure host code that copies the strings and decodes each default from the defaults image by value kind and bits (up to 64 bytes, so every v1 vector and matrix type), with no module code run. The load checks (section 3) run on the snapshot before any load, with the same rule for a loaded build and a snapshot. A project without tool scripts therefore loads no generation in the editor; it pins only the manifest's generation (below), and the store's caps apply to the rest. Snapshot descriptors are kept until the editor exits, because a loader thread may still read an older one; only a build whose descriptors changed adds one. The manifest's generation is always pinned (the pin moves to each newer manifest), so the sweep never deletes the build a game is told to load. **Staging pins** (Stage 5): a build arrives at the editor already pinned (`Outcome.pin`, taken when the store staged it, section 4); applying the outcome moves that pin into the editor's own pins (a loaded build, or the manifest's), and an outcome that is dropped or rejected releases it, so a staged build cannot be swept while its outcome waits in the main-thread queue (closes risk 20). The editor sums what it holds, with exact figures since Stage 5: the allocated bytes of the loaded generations, the bytes of the parsed snapshot descriptors the scripts keep (counted by a counting allocator while the cache is parsed) and the snapshot the build service keeps to compare the next build with (counted the same way). It warns once per session above 2 GiB: `Ziggurat has loaded <n> builds (<size>) in this editor session; restart the editor to free them.` The Zig panel shows the same figures in its memory line, `Loaded builds: <n> (<size>); descriptor snapshots: <size>` (section 9). Generation sizes are allocated blocks (section 4), not mapped memory. Loading a stripped copy into the editor (debug sections and `.strtab` removed, about 27 % of the on-disk size at 300 scripts) was dropped in Stage 7a: `dlopen` does not map debug sections, so it would save only disk, that disk is not freed while the original is pinned, it adds a copy and a strip to every loaded build, and it removes the symbols a tool-script panic's stack trace needs. Exported games never reload. Safe unloading stays deferred (decided in Stage 7b: the trash rename covers the disk on Windows, and unloading needs ABI version 3).

**Instances** hold a strong reference to their Script, an owner pointer (any Godot object), and a pointer to module-owned instance data tagged with its generation.

**The running game.** Non-tool scripts run in a separate game process.
- On save the editor tells the game to reload scripts immediately, and the build may not be done. The editor therefore writes an **atomic generation manifest** at `.godot/ziggurat/manifest`: exactly the two lines `gen=<n>` and `path=gen/<n>/<library>`, written to a temporary file, synced with `fsync`, then renamed. The game's `_reload_scripts` and `_reload_all_scripts` only set a flag; the next `_frame` reads the trusted manifest, pins and loads a newer generation and requests the swap, which runs at `_frame` under the gate. A reload that arrives before the build is staged keeps the current generation without a log line (Stage 4 logged `reload: the build may not be staged yet`); an equal or older generation is nothing to do; a refused library logs the reason and the game keeps running its current code. The script editor's save reaches the game before the build is staged (section 2). Stage 4 therefore made an editor-launched game poll the manifest about every 0.5 s; **Stage 5 replaced the polling with an explicit message**: right after each manifest write the editor's debugger plugin (`ZigDebuggerPlugin`) sends `ziggurat:reload` with data `[n]` on every active debugger session, one per running game, and sends the last written generation again when a session starts (a game reads the manifest at start, but the editor accepts its debugger connection a frame or more later). The game's `ziggurat` message capture, registered at start, turns the message into a quiet reload request for generation `n`; the next `_frame` reads the manifest through the same trusted reader, and a generation not newer than the current one is nothing to do. When the editor announced a newer generation and the manifest or library is refused, that is logged as an error. Godot's own `reload_scripts` (on a save, before staging) reads the manifest quietly: it no longer logs `the build may not be staged yet`. A game no longer watches the manifest file. In the Stage 5 GUI test (one save) the game ran the new code 181 and 195 ms after the save in two runs; with the Stage 4 polling the same test measured 452 ms. `reload_scripts` with an empty path list never reaches the language, so the editor always lists at least one script.
- **Trust.** Debugger messages (`reload_scripts`, `reload_all_scripts`) carry no trusted path; loading a library from a path you are sent is arbitrary code execution. The game reads only the on-disk manifest and loads only files inside `realpath(.godot/ziggurat)`: limits on file size and line length, no NUL bytes, a decimal generation number in range, a relative path with a fixed character set, no `.` or `..` components, no absolute paths, no symlinks that leave the folder, a regular file, a manifest that is itself a regular file and not a symlink, and a re-check right before loading. The path is tied to the generation: its resolved form must be exactly `gen/<gen>/<libName(gen)>`, otherwise `gen=3` with `path=gen/2/...` would run `ziggurat_init` again on a live module as generation 3; and a file (device and inode) already loaded under another generation is refused. Opens do not block on a FIFO, lock files that are symlinks or not regular files are refused, and the re-check right before loading compares device, inode, size and modification time. The game pins the generation it loaded, so the editor's sweep keeps its folder. All of this is implemented in Stage 3 and tested, in unit tests and in a running game (which keeps running without scripts and logs the reason). This protects against a manifest that points elsewhere, not against a hostile writer inside the folder: a hard link inside the store from generation n's path to another generation's library passes the path checks in a fresh game. A symlinked `.godot/ziggurat` folder is followed. The re-check narrows the window between check and load but does not close it; loading through an open file descriptor would. The editor side trusts the project as much as its build: the project settings `ziggurat/zig_path` and `ziggurat/dev/sdk_manifest` live in `project.godot`, so opening a project in the editor runs the Zig program that the project names and compiles the SDK modules that it lists (accepted in Stage 3). Stage 5 added the per-user editor setting `ziggurat/zig_path`, but the project setting still wins when it is set, so this trust statement still holds.
- The manifest path and the message capture exist only in debug builds and editor-launched games. Export builds compile them out with a compile-time option (no symbol and no manifest path string remain, verified in s4-game and by the host test `export build has no manifest path`).
- In an editor-launched game the manifest swap worked when `reload_scripts` arrived (Stage 0 spike s7-gui). A scene save (`EditorInterface.save_scene()`) sends no `reload_scripts` for external scripts by design; the script editor's save does when Debug > Synchronize Script Changes is on (section 2, verified in Stage 3). The game does not depend on that message: every save through the saver starts a build, and each good build that writes a manifest sends `ziggurat:reload` (above), so a scene save, or a script save with the setting off, also changes the running game. A game started outside the editor, or without the editor's debugger connection, gets no message and does not reload.

## 7. L4: script backend

Implements the full contract, with no stubs for required virtuals:
- **`ScriptLanguageExtension`:** name, type, extension (`zig`), recognized extensions, templates (never null: a null `_make_template` crashed the Create Script dialog in Stage 0; `make_template` rejects a quoted script path as parent class), `_validate` from cached diagnostics, `_handles_global_class_type`, `_get_global_class_name` (see below), `_reload_scripts` (re-read from disk, filter to own scripts), `_add_global_constant`, `_add_named_global_constant` and `_remove_named_global_constant`, `_reload_all_scripts` and `_reload_tool_script` (queue only; note `_reload_all_scripts` also fires when any other extension reloads), `_frame` (swap point under the gate), `_thread_enter` and `_thread_exit`, `_auto_indent_code` (returns input unchanged), `_get_documentation` (returns an empty array), `_supports_builtin_mode` (false), `_can_inherit_from_file`, `_validate_path`, `_complete_code`, `_lookup_code`, `_profiling_*`, `_debug_get_stack_level_*`, `_get_public_*`, and a **thread-safe, lock-free `_debug_get_current_stack_info`** that creates no StringNames (see deadlock in section 2) and is exercised once at init.
  Verified in Stage 0: `_reload_scripts` and `_add_global_constant` are required in 4.7.2 (without them the game logs an ERROR per reload and per autoload), and the editor also requires `_add_named_global_constant` once a project has an autoload. gdzig's comptime branch quota blocked five virtuals (`_add_named_global_constant`, `_remove_named_global_constant`, `_complete_code`, `_lookup_code`, `_auto_indent_code`); the vendored gdzig raises both quotas (section 13), and Stage 3 implements every virtual. `_validate` reports valid for a script whose last build succeeded; otherwise a save in the script editor never reaches the running game (section 2). `_lookup_code` returns `ERR_UNAVAILABLE`.
- **`ScriptExtension`:** `_can_instantiate` copies GDScript's rule (valid, and tool or scripting enabled, and not recovery mode); Stage 0 confirmed the gap this closes: with an always-true `_can_instantiate` and no placeholder instances, non-tool Zig scripts ran inside the editor, both during `--import` and in the GUI editor; `_instance_create`, `_placeholder_instance_create` and `_placeholder_erased`; `_update_exports` is **idempotent**: it does nothing unless the descriptor generation changed (Godot calls it once per property during scene save); `_has_property_default_value`; `_is_placeholder_fallback_enabled`; `reload` (queue; the return value is defined, and running an EditorScript requires a blocking build or a clear error); tool flag, per script (the spike kept one per generation); base type; `_is_valid`, `_has_script_signal`, `_get_script_signal_list`, `_get_members`, `_get_constants`, `_get_member_line`, `_get_rpc_config` and `_get_method_info` from the descriptors. RPC config is cached per object and never refreshed, so RPCs added by a reload are ignored; document this.
- **Global classes.** Register a global class only when the script has an explicit `pub const class_name`. A cheap text scan returns it on the scan thread, with `base_type` and `is_tool` in the returned dictionary. File names are not used as class names, because duplicates overwrite silently.
- **`ScriptInstance`** (static info table; every callback provided): set, get, property list; `call` (always sets `r_error`; unknown method returns `INVALID_METHOD`); `has_method` from the descriptor; notification (forward and reversed order); refcount callbacks (decrement returns true); `get_property_state` returns **every STORAGE property** (PackedScene and the Inspector dock depend on it); property revert; owner, script, language, to_string, free. Callbacks handle `language == null`, because host class objects can be destroyed after the host's CORE deinitialize.
- **Resource loader and saver** for `.zig`. The loader has no side effects (the editor loads a second Script object for the same path with `CACHE_MODE_IGNORE`; loaders can run on worker threads), returns the Script even if it fails to compile, and in exports resolves the script path without the source file: it answers each registered `res://...zig` path from the linked registry, fails cleanly for unknown paths, and implements `_exists` from the same registry. The saver is required, because Create Script and every script save go through `ResourceSaver`; a Script keeps the file text for the script editor apart from the code that runs. On scene save the editor saves every open script and rewrites indentation with tabs (`convert_indent_on_save`, verified in Stage 0). Zig 0.17 accepts leading tabs (verified in Stage 3); since Stage 5 the editor plugin makes `.zig` tabs indent with spaces, so a save writes spaces (section 9).
- **Editor classes** (Stage 5). Registered at the EDITOR initialization level (their parents exist only after `register_editor_types`), never exposed, and compiled out of export builds: `ZigEditorPlugin` (`EditorPlugin`; added with GDExtension's `editor_add_plugin` only when `Engine.is_editor_hint()` is true), `ZigPanel` (`EditorDock`, the Zig panel), `ZigHighlighter` (`EditorSyntaxHighlighter`), `ZigDebuggerPlugin` (`EditorDebuggerPlugin`) and, since Stage 6, `ZigExportPlugin` (`EditorExportPlugin`, handed to the editor by `ZigEditorPlugin` with `add_export_plugin`, section 10). The game side adds `ZigReloadCapture` (`Object`, SCENE level, debug builds only), whose bound `capture` method is the `ziggurat` message capture (section 6). Signal handlers are methods bound on these classes and reached through `Callable(object, method)`. Every UI call runs on the main thread. Section 9 describes what they do.
- **Shutdown.** The `ZigLanguage` object is destroyed in the SCENE-level exit (this removes the "1 ObjectDB instance was leaked" warning). Host deinit does not free pools, allocators or the registry; gdzig's stock cleanup in `entrypoint.zig` would be unsafe here.

## 8. Script shape and descriptors

A script is one `.zig` file, and the file is the struct. Example:

```zig
const z = @import("ziggurat");
const g = z.godot; // curated gdzig surface

pub const extends = g.CharacterBody2D;
pub const class_name = "Player";   // optional; required for a global class

base: *g.CharacterBody2D,   // reserved: filled in by the host, never exported
speed: f32 = 300,           // exported; every non-base field must have a default
health: i32 = 100,          // exported
title: z.String = .empty,   // exported text field: an owning SDK type
_dash_timer: f32 = 0,       // leading underscore: private, not exported

pub const meta = .{ .speed = .{ .range = .{ 0, 1000 }, .group = "Movement" } };

pub const signals = struct {
    pub const died = struct {};
    pub const hit = struct { damage: i32 };
};

pub fn init(self: *@This()) void { ... }                 // optional
pub fn deinit(self: *@This()) void { ... }               // optional; releases owned memory
pub fn migrate(self: *@This(), old: z.Previous(@This())) void { ... } // optional
pub fn _physicsProcess(self: *@This(), delta: f64) void { ... }
pub fn takeDamage(self: *@This(), amount: i32) void {
    self.health -= amount;
    z.emit(self, .hit, .{ .damage = amount });
}
```

Rules:
- Fields are exported unless their name starts with `_`. The type must convert to a Variant through the checked layer; otherwise the build fails with an error naming the field. Every non-`base` field needs a default. A field with no default is a compile error with a Ziggurat sentence; a field `= undefined` is caught with Zig's own message at an SDK line (scalars, Vector2, String, and struct-typed fields where Zig allows the check), not with a Ziggurat sentence. All fields come first in the file (Zig rejects declarations between fields).
- Field types and their Inspector hints: an enum gets hint ENUM (2) with `Tag:value,...`; a packed struct of bools gets hint FLAGS (6) with `name:bit,...`; `z.Obj(T)` of a Node class gets hint NODE_TYPE (34) and `z.Ref(T)` of a Resource class hint RESOURCE_TYPE (17), each with the class name; other object types are a compile error. Group names in `meta` are any non-empty NUL-free UTF-8 name; an empty name ends a group; groups appear in source order.
- **Text fields** use the owning SDK types `z.String`, `z.StringName` and `z.NodePath` (`.empty`, `set(borrowed)` copies, `get()` returns `*const T`). A plain engine String, StringName or NodePath field is a compile error naming the wrapper, so `self.name = arg` with a borrowed argument does not compile. These types are refused as method arguments, returns and signal arguments; a method returns text as a borrowed `*const String` (and so on) or as `z.Owned(T)`.
- Extra options live in `pub const meta`, checked against real field names at compile time. Wrapper types like `Export(f32, ...)` were rejected because they change the field type.
- `pub fn` is callable from Godot; non-`pub` is private. Engine callbacks are plain `pub fn`s found by name. Parameter names are unavailable, so exposed methods show as `arg0, arg1` unless `meta` names them.
- Signals are a nested struct; fields give argument names and types. Emitting is checked at compile time for analyzed code. The SDK makes the exported functions analyzed; bodies of unused private functions are not analyzed by Zig, so this check does not cover them. An emit that fails at run time logs one warning that names the script by its Zig type name (for example `player.hero` for `res://player/hero.zig`), not by its `res://` path: looking the path up at compile time scans every script of the generated root, which made each emitting script's analysis grow with the number of scripts (Stage 4: 66 ms per script at 300 scripts and 267 ms at 1000 in the first incremental update). Two paths can give the same type name (`a b/q/x.y.zig` and `a b/q/x/y.zig` both give `a b.q.x.y`). Compile errors still name the path.
- `get_<name>` and `set_<name>` as `pub fn` override direct field access.
- Instance memory is allocated by the host through `z.allocator(self)`. Owned memory in private fields must be freed in `deinit`. `deinit` runs while the owner is being destroyed, so it must not use `base`. A setter stores a borrowed value with `z.assign` (section 3).
- **Reload and `migrate`.** When a script's layout changes, every field with the same name and exact type identity (section 3) moves to the new instance by itself; the rest start at their defaults. The optional `pub fn migrate(self: *@This(), old: z.Previous(@This())) void` runs after that, on the new instance, and reads the old one through the old generation's field list (the new module is built without the old struct). `old.get(FT, "name")` copies a plain value (bool, integers, floats, enums, flags, vectors, `z.Obj` handles, and structs, arrays and optionals of those) and leaves the old field as it is (marked read, so it is not reported as dropped). `old.take(FT, "name")` moves an owning value (`z.String`, `z.StringName`, `z.NodePath`, `z.Ref(T)`) out; the old field is then reset before the old `deinit`, so the value is released once. A field the host already moved, or an earlier `take` took, gives null. `old.takeInto(FT, &self.field, "name")` is `take` into a field that may already hold a value: it releases that value first. Each gives null (or false) for a missing field or another type; nothing panics. `get` on an owning type or `take` on a plain one is a compile error. Owning types are allowed only as top-level fields (a `z.String` inside a struct, array, optional or union field is a compile error), because only top-level fields are released and moved. `migrate` runs under the gate's write side; a call from it into the instance being migrated is refused (section 6). `migrate` and `deinit` must not wait for another thread or for a lock another thread may hold while it calls a script: that thread waits at the gate during a swap, so the wait never ends (section 6).
- `base` can be any Godot object. Tool scripts: `pub const tool = true;`. `extends` takes an engine class in v1; the class name comes from an explicit `class_name` declaration, because `@typeName` of the type is a long path.

**Descriptors.** `ziggurat_describe` returns the table of section 3. Per script: path, class name, base class, tool flag, the field list with type identity and value kinds (section 3; the host computes the layout hash from it), a defaults image (every field at its default, used to reset moved fields, to fill new ones at migration and, through the snapshot, for the Inspector's defaults without module code); per property: name, Variant type, hint, hint string, usage, default (from field defaults, evaluated at compile time); per method: name, argument types, return type, flags; per signal: name, argument names and types; plus the generated wrapper pointers. The call wrapper checks each Variant argument through the checked conversion layer and returns Godot's call-error code on mismatch instead of panicking. The host saves a typed JSON copy of the descriptors the editor needs after every good load (`.godot/ziggurat/descriptors.json`, section 6).

## 9. L5: editor plugin

As built in Stage 5 (`src/host/editor_plugin.zig` and its neighbours). The plugin is part of the host library, registered at the EDITOR initialization level (section 7) and absent from export builds. It talks to the editor's build code only through a small API in `src/host/editor_build.zig`: request a build, read a status copy (building or not, and the last outcome: generation, whether the editor took it into use, trigger, path, time, error and warning counts, `ZigProblem`), copy the diagnostics, and apply finished outcomes at once. Errors also reach the script editor through `_validate` (section 7). Script templates are section 7.

**Settings.** Project settings: `ziggurat/zig_path` (the per-project override of the Zig path, section 4), `ziggurat/dev/sdk_manifest` (a developer override for the editor's own target; empty by default, so the shipped SDK in `addons/ziggurat/sdk/<target key>/` is used, section 5), `ziggurat/build/build_on_play` (default true) and `ziggurat/build/play_wait_seconds` (default 60). Editor (per-user) settings: `ziggurat/zig_path` (with a file picker), `ziggurat/editor/indent_with_spaces` (default true), `ziggurat/build/check_interval_seconds` (default 0; 0 to 3600 in the inspector; 0 means focus-in, plus every 2 s while a game runs), and since Stage 7a `ziggurat/build/debugger_builds` (default false) and `ziggurat/build/backend` (default `auto`, an enum in the inspector; section 5). A `play_wait_seconds` that is a float is rounded to the nearest second; a negative number, a non-finite float or another type (such as a string) reads as the default 60. There is no script-folder setting: `.gdignore` already keeps folders out of the scan.

**The Zig panel** is a bottom `EditorDock` titled `Zig` (`add_dock`, not the deprecated bottom-panel call). It has a Build button (`Building...` while a build runs), a status line for the last applied build, `Build <n> ok (<trigger>, <path>, <ms> ms)`, `No Zig scripts; nothing to build` (section 5), or `Build failed: <e> errors, <w> warnings (<ms> ms); build <n> stays in use` (or `no build is in use`), a memory line (section 6), the line `Debugger builds: on (slower, no incremental)` while that setting is on (section 5), a download row (below) and a `RichTextLabel` with the failed build's message and every diagnostic of the last build, in report order. Each diagnostic in a project file starts with a `res://path:line:column` link that opens the script at that place (`EditorInterface.edit_script`, 1-based). A diagnostic outside the project's files is plain text without a link. The error of a withheld gdzig helper is not one of them: it is reported at the script line that names the helper (section 13). The Project > Tools menu has `Build Zig Scripts` and `Download Zig 0.17.0`. Toasts: a warning toast `Zig build failed: <e> errors, <w> warnings; build <n> stays in use. See the Zig panel.` when a build fails while a good build is in use, and an error toast when no usable Zig was found (`ZigProblem` other than none) that names the problem and points to the download and to the editor setting. An outcome applied before the panel exists gets its toast at the first frame after the panel is added.

**Build on Play** (`_build`; Godot calls it on the main thread when Play is pressed, after it saved the open scenes and scripts, and the run waits for the answer). Without a build service (no SDK: neither the shipped one nor the manifest setting; or a non-interactive editor run) or with `build_on_play` off it returns true at once. A project with the add-on but without Zig scripts gets a good empty build (section 5), so Play runs without Zig. Otherwise it requests a `play` build, waits up to `play_wait_seconds` for the service and applies the outcome on the spot, so the manifest names the new build before the game starts. A good build plays. A failed build cancels the run and shows the Zig panel, as C# does. After the timeout the game starts if a good build exists, with the toast `Zig build still running; the game starts with build <n> and reloads when the build finishes`; the reload message brings the new build when it is staged (section 6). "A good build exists" means the build the editor took into use in this session or, without one, the generation the manifest on disk names when the manifest and its library pass the game's own trust checks, so Play right after opening a project still runs the last session's build. Without any good build a timeout cancels the run. Where the main-thread queue may not run (module code on the main thread's stack, as when a tool script starts Play, or a drain of the queue running; the rule of `_frame`, section 6), Play neither waits nor applies an outcome: it requests the build and decides at once, true with the toast while a good build exists, otherwise false with `Ziggurat cancelled the run because Play was started while Zig code or a build update ran on the main thread, so it could not wait for the Zig build, and no good build exists yet; see the Zig panel.` A round of the wait that applied nothing pauses for 1 ms, so the wait never spins. Applying a loaded build takes no second pin for the manifest (the load pin holds the generation until exit), so it never waits for the store lock of a staging copy that runs at the same time; Play returns within `play_wait_seconds` plus the time to apply the outcomes that waited.

**Syntax highlighter.** `ZigHighlighter` (`EditorSyntaxHighlighter`, name and language `Zig`) is registered with the script editor when the plugin enters the tree and overrides `_create`, so every `.zig` tab gets its own. A std-only line highlighter (`src/host/highlight.zig`) cuts each line with `std.zig.Tokenizer` (Zig has no token that spans lines other than `\\` lines, each of which ends at its line end) and maps tokens to Godot's `text_editor/theme/highlighting/*` colours: control flow (`if else switch while for return break continue try catch orelse defer errdefer unreachable`) to `control_flow_keyword_color`; other keywords and `true false null undefined` to `keyword_color`; primitive types to `base_type_color`; identifiers that start with an upper-case letter to `user_type_color`; `@builtins` and identifiers followed by `(` to `function_color`; numbers, strings, `//` comments and `///`/`//!` doc comments to their colours; the rest to `symbol_color`. It reads the line with `TextEdit.get_line_with_ime`, as GDScript does. Columns count code points, as Godot's `String` and `CodeEdit` do (section 2). Bounds for hostile text: at most 512 regions per line, and no token that starts after the first 64 KiB of a line is looked at (the rest keeps the last colour), so a 1 MB line stays quick; invalid UTF-8, NUL bytes and unterminated strings cannot crash it.

**Indentation.** Godot has one indentation setting for all languages (tabs by default) and converts a file to its tab's indentation on save. With `ziggurat/editor/indent_with_spaces` on, the plugin sets `indent_use_spaces` and an indent size of 4 on the `CodeEdit` of every open `.zig` tab, so a save writes spaces, as `zig fmt` does. Godot resets every tab when a `text_editor` setting changes, so the plugin applies its values again at the next frame after that notification, after each `settings_changed` signal, when a tab opens or changes (`editor_script_changed`) and at focus-in. Tabs are matched to scripts by order: `ScriptEditor.get_open_script_editors` and `get_open_scripts` both list tabs in order; when their counts differ, only the current tab is set. With the setting off the plugin sets Godot's own choice.

**External edits.** At focus-in, on the optional interval, and every 2 s while a game from the editor runs and the interval is 0, the plugin asks for a `watcher` build that runs only when a file changed (section 5). An unusable Zig path logs one warning, `Ziggurat: the Zig path is not usable, so changed files are not checked: <reason>`, until a check finds the path usable again.

**Zig download.** `Download Zig 0.17.0` (Project > Tools) fetches the official release for the editor's platform once into a per-user folder (`<toolchains>/zig-0.17.0`, where `<toolchains>` is the path service's toolchain folder `<user data>/ziggurat/toolchains`; on Linux `$XDG_DATA_HOME/ziggurat/toolchains`, by default `~/.local/share/ziggurat/toolchains`), shared by all projects, never into the project. It runs only when the user asks; the editor never downloads on its own, and an export build has no download code. Network access goes only through Godot's `HTTPRequest`, so no network library is linked into the extension. As built:
- **Pins** (`src/platform/pins.zig`): for each target the archive name, size and SHA-256 of Zig 0.17.0, checked in addition to the signature. x86_64 Linux and, since Stage 7b, x86_64 Windows (`zig-x86_64-windows-0.17.0.zip`, 100,268,137 bytes) are active, so the Windows editor offers the download; aarch64 Linux and both macOS targets are listed but not offered. On Windows the toolchain folder is `%LOCALAPPDATA%\ziggurat\toolchains`. The Windows download was tested under Wine with the real zip and its real signature from a local server: the pinned hash and key pass and the installed `zig.exe version` prints `0.17.0`. Zig's minisign public key is pinned (`RWSGOq2NVecA2UPNdBUZykf1CCb147pkmdtYxgb3Ti+JO/wCYvhbAb/U`).
- **Mirrors.** The community mirror list (`https://ziglang.org/download/community-mirrors.txt`, at most 64 KiB, status 200) is cached in `<user data>/ziggurat/mirrors.txt` for 24 hours (a future modification time counts as stale). The parse is strict and all-or-nothing: each line is `https://`, a host, an optional port and a plain path; at most 256 mirrors. A list that cannot be fetched or parsed falls back to an older cached copy that parses, else to ziglang.org alone. The mirrors are shuffled with a ChaCha CSPRNG seeded from the system's random source, and ziglang.org (`https://ziglang.org/download/0.17.0/<file>`) comes last. Both requests carry `?source=ziggurat`.
- **Per mirror:** the `.minisig` into memory (at most 4096 bytes, status 200), checked at once for everything but the file signature (the `ED` form, the key id, the global signature and the `file:` name), so a bad signature file moves to the next mirror without the archive transfer; then the archive into `<toolchains>/.download-<random>` (at most the pinned size, status 200). Redirects are followed, also from https to http, which is safe because nothing is trusted before the checks. Limits: the list and signature requests time out after 30 s; an archive transfer that receives no new byte for 60 s fails the mirror (stall watchdog); and each archive transfer has a deadline of the pinned size at 32 KiB/s, at least 5 minutes, so a mirror that trickles cannot hold the run. Any failure deletes the mirror's temporary file, logs the mirror and the reason, and tries the next mirror.
- **Transfers on the main thread.** `HTTPRequest` runs with `use_threads` off, polled each frame, at most 1 MiB per frame, because a threaded transfer froze the editor on cancel and exit (section 2). The transfer speed is therefore tied to the editor's frame rate.
- **Check and install** (`src/platform/toolchain_install.zig`, std only) on a worker thread, under the toolchain lock `<toolchains>/.install.lock`, so two editors never install at once. Order: archive name, size, SHA-256, minisign signature, then unpack. The signature must be the prehashed `ED` form (BLAKE2b-512; the legacy `Ed` form is refused), with the pinned key id, a valid file signature and global signature (Ed25519 `verifyStrict`), and exactly one `file:` field in the trusted comment equal to the requested archive name, which blocks a downgrade to another signed release. The unpack goes into `<toolchains>/.zig-0.17.0.tmp-<random>/` from the same open file: tar.xz through `std.compress.xz` and an own tar loop (regular files and folders only; links, `..`, absolute names, `\`, `:` and control characters refused), zip entry by entry with the same name rules plus Windows device names. The tar.xz bytes are hashed again while they are unpacked; the zip bytes are hashed again after the unpack, because std's zip reader seeks. On Windows the installer opens the archive once with `CreateFileW` and `FILE_SHARE_READ` only (`win32.openReadShareRead`), so while the install runs no other process can open the file for writing or deleting; the same handle serves the check, the unpack and the hash after it. std's open shares write and delete, and its `.lock = .shared` calls `NtLockFile`, which Wine does not run. A changed file fails the install (on Linux nothing stops a writer, so this check is what catches it). The xz stream must end with its index and footer (a cut at a block end is otherwise a normal end, section 2). The result must be exactly one top folder `zig-<arch>-<os>-0.17.0/` with the `zig` executable and `lib/`; `zig version` must print `0.17.0`; then the folder is renamed to `zig-0.17.0`. If a working `zig-0.17.0` appeared meanwhile (another editor won), it is kept; a broken one is replaced. Every failure deletes the temporary folder; nothing unchecked is ever moved into place or used. If a working `zig-0.17.0` exists already, the download does not start.
- **Memory.** Std xz decodes the single block of the release (372 MiB) in memory: about 890 MiB peak for a few seconds. The panel says so while it runs: `Checking and unpacking Zig (needs about 800 MB of memory)`.
- **In the editor.** The panel's download row shows the state (fetching the mirror list, downloading with the mirror and bytes, checking, `Zig 0.17.0 installed`, or failed with the reason) and a Cancel button that stops a transfer; the check cannot be stopped and ends by itself. A second click while a download runs is ignored. After an install the editor asks for a build (`manual`), so the locator finds the new Zig. A failure shows one error toast, `Ziggurat could not download Zig 0.17.0: <reason>`, and the panel. At editor exit a transfer is cancelled and a running check is waited for, so no thread outlives the library and no temporary file stays. What a crash leaves is deleted at the next download's start, under the toolchain lock (skipped while another editor holds it): `.download-*` files and `.zig-*` entries with `.tmp-` or `.old-` in the name, when older than one hour (a running download of another editor writes its file every few seconds); `zig-0.17.0` is never touched.

## 10. Export

The export plugin builds one library per target platform with every script linked statically and registered at startup (no dynamic module loading, no `dlopen`), and uses a deterministic release build, not the editor's last build. Scenes reference `res://x.zig`, but sources are left out of the package: an `EditorExportPlugin` skips every `.zig` file, and the host's loader answers the path from the linked registry (section 3). Godot 4.7.2 release builds hand `res://x.zig` to the loader without checking that the file exists (the existence check is editor-only), so no stub file is needed (verified, Stage 0 spike s5-export, and in Stage 6 with the real release template; a stub file per script, as C# does, stays the fallback if a later Godot checks first). The plugin is required: a default export ships `.zig` sources verbatim. Web and iOS require static linking, which this design already uses. Android needs the NDK for libc builds.

**As built in Stage 6, with Windows from Stage 7b** (`src/host/export_plugin.zig`; Linux x86_64 and Windows x86_64 in this version, from either editor).
- **`ZigExportPlugin`** (`EditorExportPlugin`, EDITOR level, never exposed, compiled out of export builds) is created in `ZigEditorPlugin._enterTree` and handed to the editor with `add_export_plugin`, and taken back in `_exitTree`. `_get_name` is `Ziggurat`, which is also the category of its messages. `_supports_platform` is true for every platform, so Godot adds no warning of its own on top of the plugin's message. `_export_file` calls `skip()` for every path that ends in `.zig` (any case).
- **`_export_begin`** runs before Godot writes anything. It maps the preset's features to a target key (`target_key.fromFeatures`, section 4). A preset without a packaged key (not `linux` + `x86_64` or `windows` + `x86_64`) gets the error message `Ziggurat exports Linux x86_64 and Windows x86_64 in this version` and nothing else: such an export finishes "with warnings" and without Zig scripts (Godot also warns that it found no library for the platform). For a packaged key the plugin first sweeps libraries an earlier Windows export renamed aside (below), then removes the game library `res://.godot/ziggurat/export/<key>/<library>` (`x86_64-linux/libziggurat_game.so` or `x86_64-windows/ziggurat_game.dll`), so a library of an earlier export can never ship. A full export also deletes that library in its output folder (the folder of the export path), so a failed export does not leave the previous export's library next to the new game files (when that delete fails, an error names the file). Then it scans the project (the build service's scan, which skips `addons/`):
  - **Scan problems fail every export** (Stage 7a, with or without Zig scripts): a `.zig` file the scan cannot read, a folder it cannot open or list, and two scripts that differ only by case. Such a file may be a script that a scene uses, and an export without it would ship a game that silently lacks it. The plugin sends each problem as an error, ends with `Ziggurat cannot export the project's Zig files: the scan found the problems above, so it does not build the game library.` plus a remedy (fix the permissions, or add a `.gdignore` file to a folder that holds no scripts), and builds and copies nothing, so the export fails. The export build checks its own scan the same way (section 5). Editor builds still only report scan problems.
  - **With Zig scripts** it finds the Zig, the SDK and the per-user cache folder the editor uses (`editor_build.exportInputs`, which needs no running build service, because an `--export-*` run starts none) and the export host archive of the target (`addons/ziggurat/bin/<key>/libziggurat_host_export.a` or `ziggurat_host_export.lib`), prints `Ziggurat: building the game library for the export (<n> Zig scripts, Zig <version> at <path>)...`, runs the export build (section 5) on the main thread, and prints `Ziggurat: export library built in <ms> ms: <path>`. Before it builds (Stage 7a, closes risk 33), it compares the SDK's `sdk_version` (from the running build service or the manifest) with the editor host's; when they differ, the export fails and writes nothing, with `Ziggurat cannot export: the SDK at <manifest path> is version <x>, but this add-on's export library (addons/ziggurat/bin/<key>/<archive>) needs SDK version <y>.` followed by `Clear the project setting ziggurat/dev/sdk_manifest, or install the add-on that matches the SDK.` when that setting is set, or `Reinstall the add-on.` when it is empty. The scan check comes first. Only the version is compared: a developer SDK with the same version but another layout still exports, and the game then refuses the linked table (the link-time stamp symbol is not done).
  - **Debug export** (Stage 7a). When Godot's `is_debug` is true (`--export-debug`, Export With Debug), the export build passes `-fno-strip` instead of `-fstrip` and logs `Ziggurat: debug export keeps debug information, with this computer's file paths, and is not reproducible. Turn off Export With Debug for a release.` The library then holds absolute paths (so the build machine's user name too) and differs per project folder (risk 34). Godot ticks Export With Debug by default in its export dialog, so a default GUI export is a debug export; the add-on's README says to untick it for a game that ships. Release exports are unchanged. A Windows debug export (Stage 7b) differs: the compiler writes the debug information to a separate `.pdb` file in the build cache, which the export does not ship, and the DLL holds only that file's name, so the log line is `Ziggurat: debug export writes the game library's debug information to a separate .pdb file in the build cache, which the export does not ship; the library keeps only that file's name. Turn off Export With Debug for a release.` (`debugExportLine(key)`).
  - **Without Zig scripts** it copies the add-on's **empty game library** `bin/<key>/libziggurat_game_empty.so` or `ziggurat_game_empty.dll` to the output path. That library is the export host archive linked with the generated root of no scripts (`src/build/empty_root.zig`, checked against `rootgen` by a unit test; the Windows one with the hidden root and the `.def` file), built like an export build (730,320 bytes for Linux and 1,006,592 for Windows in Stage 7b; the package test checks that each exports only `ziggurat_host_init`); the game logs `ziggurat: 0 scripts linked`. No Zig and no SDK are needed. Without it, the missing library would fail every export of a project that has the add-on but no Zig scripts (section 2). Scan problems fail this path too (above).
- **Failures.** Every failure becomes an error in the export's message list (`add_message`, which also prints it): each compile diagnostic as `res://<file>:<line>:<column>: <message>` (at most 50, then a count), then one summary sentence that ends `This export fails: the files in the export's output folder are incomplete.` An error message alone does not fail a Godot export (section 2), so **the export fails through the missing library**: on every failure path the game library does not exist, Godot's GDExtension export cannot copy it ("Failed to copy shared object"), the export is reported as failed and a headless export exits with status 1. Godot has already written `<game>.x86_64` and `<game>.pck` into the output folder by then, so a failed export leaves an incomplete game there (the README says not to ship it). The paths that fail: a compile error, a failed library check, a missing or wrong-version Zig, no SDK, a missing export host archive, a busy build lock after 120 s, scan problems (with or without scripts), an SDK of another version, out of memory.
- **An old library that cannot be deleted** (for example, the folder is not writable) is emptied and then gets file mode 0 (removing permissions needs ownership of the file, not write access to the folder), so Godot cannot copy it and the export fails as above; the message says so and asks the user to delete the file. If even the mode cannot be changed, the plugin cannot make the export fail, and the error says exactly what ships: an empty game library whose game cannot load its Zig scripts, or, when the file could not be emptied either, the old library with the scripts of an earlier export. That is the POSIX rule (`fromMode(0)` stays POSIX-only).
- **An old library on a Windows editor** (Stage 7b; a DLL another program has loaded or holds open cannot be deleted). In order: delete it; if that fails, rename it to `<library>.old-<16 hex>` in the same folder with `MoveFileExW` (a loaded DLL can be renamed) and log `Ziggurat: the game library of an earlier export <path> is in use, so it was renamed to <path>; the next export deletes it.`; if the rename fails too, fail with `Ziggurat cannot replace the old game library <path>: <delete error> (renaming it aside failed: <rename error>). Close programs that use it and export again.` and build nothing. Each export first deletes the renamed libraries it finds, and only names in exactly that form.
- **A stale library copied anyway** (Stage 7b, every OS). When the old library could not be removed, Godot can still copy it next to the game (a file held without delete sharing is still readable). `_export_end` therefore removes the library the export copied: `<output folder>/<library>` for a full export, or the zip when this export wrote it and it holds the library (or cannot be read), and logs `Ziggurat deleted …`; if that delete fails, the error says that this export ships the old game library of an earlier export and asks the user to delete it. A `.pck` export is left alone: Godot copies no library into a pack. Tested under Wine with a DLL held open without delete sharing and with a loaded DLL.
- **Pack exports.** Zig scripts are only exported with a full export. A PCK/ZIP export and a patch export (Export PCK/ZIP, `--export-pack`, `--export-patch`) run `_export_begin` too, but write only a pack: Godot copies shared libraries only in a full export, so the pack never contains the game library. A pack used with the game library of an earlier export would run that export's Zig code (and scripts that library lacks would not load), silently. Godot passes no pack or patch flag to `_export_begin`, so the plugin decides from the path as Godot routes it: a path ending in `.pck` is a pack; a path ending in `zip` is a pack or a full Linux export that Godot zips (both give `_export_begin` the zip path), so `_export_end` reads the written zip's central directory and treats it as a pack when no entry is named after the target's game library (`libziggurat_game.so`, `ziggurat_game.dll`) (unless the zip was not written or is an earlier export's file). For a project with Zig scripts the plugin still builds (so errors show), and then sends the error `Ziggurat exports Zig scripts only with a full export: this PCK/ZIP export does not contain them.`, which says why and asks for a full export. Godot gives an export plugin no way to stop a pack export: the pack is written, a headless pack export ends "completed with warnings" with status 0, and the editor's Export PCK/ZIP opens no result dialog, so the error shows in the Output panel only (code reading of `ProjectExportDialog`). The errors of a `.pck` export therefore do not end with the "This export fails" note; those of a `zip` export do, because it may still be a full export until the zip is written. A project without Zig scripts gets no message.
- **`.gdextension`** (`addons/ziggurat/ziggurat.gdextension`): `entry_symbol = "ziggurat_host_init"`, `compatibility_minimum` and `compatibility_maximum` `4.7`, `linux.editor.x86_64 = "bin/libziggurat_host.so"`, `linux.template_debug.x86_64` and `linux.template_release.x86_64` both `res://.godot/ziggurat/export/x86_64-linux/libziggurat_game.so`, and since Stage 7b `windows.editor.x86_64 = "bin/ziggurat_host.dll"` and `windows.template_debug.x86_64` and `windows.template_release.x86_64` both `res://.godot/ziggurat/export/x86_64-windows/ziggurat_game.dll` (Stage 6 used `linux.x86_64/`, which is no longer used). The template keys point at the file the export plugin writes, so Godot's own GDExtension export copies it next to the game; the file does not exist until an export builds it (the README says not to change the keys). A game started with Play from the editor has the `editor` feature too, so it keeps the editor library and reloads as in Stage 5.
- **Closed open gaps** of the Stage 0 spike: the export uses the deterministic ReleaseSafe build; scenes that reference a script only by uid, with a wrong text path, run in the exported game; release templates reject `--main-pack`, so the tests run the `<game>.pck` next to the binary. A script added after the last editor build is in the export, because the export always builds the current sources.
- **A Linux export from a Windows editor** has no executable bit on the game (section 2); the README says to run `chmod +x` on it. Tested under Wine for a project without scripts only.
- **Not done in this version:** macOS libraries and their export (Stage 7c), other architectures, Web, iOS and Android (later). A Windows export of a project with Zig scripts from a Windows editor is unproven (risk 35). The export blocks the editor's main thread while it builds, with progress lines but no progress dialog (risk 25).

Against the bounds the median body edit still fails, narrowly at 300 (131 against 100 ms) and at 1000 (428 against 200 ms); the first edit is flagged at 1000 only; the field-default edit passes at both. The driver time includes the scan, the generated root, the staging copy and the table check, about 50 ms at 300 and 200 ms at 1000 more than the compiler update alone (84 and 223 ms in the review's compiler-only measurement). What remains per body edit is a per-update compiler cost of about 0.2 to 0.3 ms per script outside analysis, code generation and linking. *Session start and warm-up:* the SDK's comptime work per script, `describe` and the generated wrappers, costs about 170 to 220 ms of analysis per script (96 % of all analysis); the first incremental update spends 2.6 times the analysis time of a non-incremental build on the same code, so warm-up is about 2.5 times the session-start build. Making `describe` and the wrappers cheaper is the first Stage 4 item, before the bounds are frozen. The first two candidates, measured at 50 scripts: `@hasDecl` in place of the linear `isPub`/`hasPub` scans (about 45 ms per script) and a name-collision check that only looks at names a rename or snake-casing changed (removing the check saved about 44 ms per script); together they cut analysis by 47 % and the non-incremental 300-script build from 26.5 to 15.0 s.

Two drivers. *Service driver* (the Stage 3 method and shape, without signals): `BuildService` with the table check, as the editor runs it, fresh project cache, prebuilt gdzig bindings; each edit time includes scan, generated root, compiler update, staging copy and table check (with the Stage 4 table snapshot about 17 ms at 300 scripts and 56 ms at 1000).

## 13. Upstream work and pins

- **gdzig is vendored** in `vendor/gdzig/` at the pinned commit with exactly five patches, listed in `vendor/gdzig/PATCHES.md`. Patches 1 and 2: `virtualMethodNames` (`src/extension/class.zig`) gets a comptime branch quota of 10000 (it had none, so Zig's default of 1000 applied) and `VTable.findMethod` (`src/class/vtable.zig`) one of 1000000 (was 100000); the smallest values that compile `ZigLanguage` with all 60 `ScriptLanguageExtension` virtuals are 1825 and 186392. Patch 3 (Stage 5): the build option `object_helpers: bool` (default true, so the default build matches upstream). With false, the six Object helpers that bindgen copies into every engine class (`setInstance`, `asInstance`, `connect`, `disconnect`, `emit`, `emitAlloc`) are `@compileError("ziggurat: <name> is not available in scripts; use z.emit or z.godot.Callable")`: the instance binding belongs to the host, and `connect`/`emit` would bypass the SDK's checked `z.emit` and `z.godot.Callable`. Ziggurat's `build.zig` builds the SDK's gdzig (and so every script) with false and the host's with true, which makes two gdzig dependency instances in one build (no measurable change in `zig build test` time). The compiler reports the error at the constant in gdzig's generated class file (for example `gdzig/class/Node.zig`); the diagnostics map it to the first frame of its reference trace in a project file, which is the script line that names the helper, so the panel and `_validate` show the script (section 5). Patch 4 (Stage 6): gdzig imported the package `oopz` for its class checks (`isClass`, `isA`, `BaseOf`, `upcast` and the rest that `gdzig.class` re-exports), and `oopz` has no licence (section 2), so it could not ship in the host, the export archive, the SDK or any game. On the user's decision (2026-10-24) it is replaced by gdzig's own `src/class_kind.zig` (MIT, as gdzig), written clean-room: its author did not read `oopz`'s source, only gdzig's call sites and tests. The public names in `gdzig.class` are unchanged; `oopz` is gone from gdzig's `build.zig`, `build.zig.zon` and the SDK. The model: an engine class is an `opaque` with a `Base` declaration (`void` at the root); a user class is a `struct` whose `base` field is a mutable single-item pointer to a class or an embedded user class. Its own edge-case choices: a `*const` class pointer counts as a class pointer; a `const`, optional or many-item `base` pointer does not make a class; `upcast` refuses optionals and dropping `const`. The class walks carry the classes already passed: a `base` field or `Base` declaration that leads back to one of them (a struct whose `base` points at its own type, two structs that point at each other, an `opaque` whose `Base` is itself) never reaches `Object`, so the type is not a class, and the caller gives its own compile error (`z.Obj`: "is not an engine class type"; `Callable.init`: "needs a pointer to an engine class instance"). Before the final review of Stage 6 such a type crashed the compiler (risk 30). A chain of more than 64 classes is a compile error that names the type; the walks' branch quota is 1000000. `PATCHES.md` lists every compile-error case (`assertIsA`, `assertIsAny`, `upcast`, `BaseOf`, the depth limit) with its message and how to repeat it. Patch 5 (Stage 7a): thread-safe lazy caches (risk 17, closed). `fromComptimeLatin1` (`src/builtin/StringName.mixin.zig`) uses the three-state claim of section 3: a compare-and-swap picks the one thread that stores the value, which it publishes with a release store; a loser returns its own copy and never frees it. Every plain single-pointer cache in gdzig uses `@atomicLoad(..., .acquire)` at the null check and at the call and `@atomicStore(..., .release)` at the fill: the generated method binds, builtin constructors, destructor, operators and method pointers, utility functions and singleton `instance` (`pkg/bindgen/codegen.zig`), and the hand-written `isClass_legacy_ptr` and singleton read (`Object.mixin.zig`), the two legacy binds of `RichTextLabel.mixin.zig` and the two Variant converter caches (`variant.zig`). The plan named fewer sites; the patch covers every plain cache, because any one left would keep the race. Several threads may store the same pointer. ThreadSanitizer found the race in `fromComptimeLatin1` before the patch (section 11). Patches 1 to 3 go upstream; patches 4 and 5 can be offered as well (patch 5 fixes a data race in upstream gdzig as it is). Until then every gdzig upgrade re-applies them.

## 14. Risks

1. gdzig API churn (README warns of rapid change). Mitigated by the wrapper layer, the curated SDK and the commit pin.
2. Script-language traps in Godot. Mitigated by the checklist in section 7.
3. Incremental compilation is young and expensive to warm up. It is only the fast path.
4. Windows and macOS are unverified on real hardware. Windows is built and tested under Wine 11.19 only (Stage 7b, risk 35); macOS is Stage 7c and ships untested. The design avoids Linux assumptions, but that is a claim until real hardware runs it.
5. Memory and disk grow with each reload in long sessions (no unloading in v1). Incremental outputs are sparse files about 2.7 times the non-incremental size, multiplied by kept generations. The compiler server grew from 1.4 to 2.0 GB at 1000 scripts over nine updates after warm-up (Stage 0); with the real SDK the largest compiler process reached 2.9 GB at 1000 scripts and a staged module 1.29 GB of apparent size (Stage 3). Measured in Stage 4: in the 300-edit stress run (five small scripts, 289 generations loaded in one editor) the editor's resident memory (`VmRSS` from `/proc`, sampled about twice a second) grew from about 800 MiB early in the edit loop to about 970 MiB, with a peak of about 990 MiB, so about 0.7 MiB per loaded generation for small modules; large modules map more. Since Stage 4 a project without tool scripts loads no generation in the editor, but each build whose descriptors changed keeps its snapshot descriptors until the editor exits: about 7.8 MB per such build at 300 scripts (measured on the parsed cache for the timing shape; the cache file is 3.7 MB). Since Stage 5 the 2 GiB warning and the Zig panel's memory line count these descriptors exactly (a counting allocator while the cache is parsed, plus the build service's kept snapshot), so the warning no longer undercounts them; the loaded builds are still counted by their allocated bytes on disk, not by mapped memory. A long session of field edits on a large project without tool scripts can therefore hold gigabytes without a reload of code.
6. A user-code panic in a tool script kills the editor and can leave the project in recovery mode. This cannot be recovered; it is reported clearly.
7. State migration is tested with threads, nested `Main::iteration()` and callbacks during a migration from a test hook standing in for `migrate` and `deinit` (no test script's own `migrate` or `deinit` calls back; Stage 4, sections 6 and 11), but only on x86_64 Linux and with synthetic scripts. A `migrate` or `deinit` that calls into the instance being migrated gets an error, not its data. Calls on one instance from two threads are not serialised. A moved slice or pointer field that points into an old module's constant data stays valid only because old generations are never unloaded (risk 13).
8. Incremental compilation can keep old code with 0 errors. Two cases are known: a generic `@export` went stale after a field change (Stage 0), and in Zig 0.17 a function that took a field's address from a comptime value kept the old field offsets after the struct's layout changed (Stage 4: the SDK's `get_default` returned wrong defaults and crashed on owned fields; section 2). Mitigated by root-owned exports, a run-time copy in `get_default`, and the checks after each update (section 5): the build id, the layout-drift rebuild and the defaults check. The defaults check has limits. It runs only on builds the editor loads, so it never covers a build the editor does not load (a project without tool scripts) and never runs in the game, which loads the manifest's build without it. It compares plain defaults first and bit for bit, does not compare vector defaults with non-finite components, and a stale read of an owned (text) default is caught only when a plain default of the same build also differs; a stale `get_default` that reads only owned fields can still crash inside the check. A build it rejects stays loaded and pinned for the session, like every loaded build, until a later sweep after the editor exits. Other code that takes a field address from a comptime value could be miscompiled the same way; the SDK no longer does, but user code can.
9. gdzig is vendored with five patches (two quotas, the `object_helpers` option, the own class checks that replace `oopz` and the atomic lazy caches, section 13). Until they are upstream, every gdzig upgrade must re-apply them, and the vendored copy adds about 13 MB to the repository.
10. Live reload into an editor-launched game does not depend on Debug > Synchronize Script Changes: since Stage 5 the editor sends `ziggurat:reload` after every manifest write and again when a debugger session starts (section 6), so every good build that writes a manifest reaches the game, including one started by a scene save or by a script save with that setting off. It depends on the editor's debugger connection: a game started outside the editor, or with the debugger off, never reloads. The `reload_scripts` message the setting sends still depends on `_validate` reporting the script valid (section 2); the game handles it as a quiet manifest read. The script editor's save path is tested under Xvfb; one manual run on a real desktop is pending.
11. GUI editor coverage is automated only, on a virtual X display; one manual run on a real desktop is pending (section 12, Stage 0 item 7). The Zig panel, toasts and the download are tested in the headless editor and against a local fixture server; opening the panel and downloading the real Zig on a real desktop is an optional manual check.
12. A damaged module file can load if its size is consistent: the ELF check before loading, and on Windows the PE check (Stage 7b: headers and every section's raw data inside the file), are not integrity checks (section 6). The ELF check skips the section-table bound when `e_shnum` is 0 (extended section numbering; Zig output does not use it). A content hash written by the build would close the gap on both.
13. Safe unloading (deferred again in Stage 7b; needs ABI version 3) has two known traps: each script's defaults image points into the module's read-only data, so a module must not be unloaded while a table or a moved field still refers to it; and instances freed after the host's shutdown at SCENE exit leak their data.
14. The downloaded Zig on macOS is only ad-hoc signed, not notarized. A copy fetched by Godot carries no quarantine flag and should run; a copy the user fetches in a browser is blocked by Gatekeeper until the flag is removed. Not tested on a real Mac (stage 7). On Windows, some antivirus products have flagged Zig and Zig-built programs as false positives; Ziggurat's DLLs are unsigned (the user's decision), and neither antivirus nor SmartScreen behaviour was tested (Wine only).
15. The Asset Store is labelled beta, lists free assets only, and its rules may change. The release zip is the fallback channel with the same contents.
16. The session-start build and the median body edit are still above the provisional bounds at 300 and 1000 scripts after the Stage 4 SDK work (section 12: 12.0 s and 42.7 s, 127 ms and 512 ms), although session start and warm-up are about twice as fast as in Stage 3. What remains is mostly the SDK's per-script checks and property building (`desc` and `properties`, about 58 of 93 ms of analysis per script) and a per-update cost that grows with the number of scripts. The slow path stays correct; the user decides on the bounds (section 15).
17. Closed in Stage 7a: the SDK's and gdzig's lazy caches were a plain flag and a plain value, so on a weakly ordered CPU (arm64) a reader could see the flag before the value, and ThreadSanitizer showed that two threads also wrote the multi-byte value at once. They now use a compare-and-swap claim with release and acquire ordering, and gdzig's single-pointer caches atomic loads and stores (section 3, patch 5 in section 13); a ThreadSanitizer test runs in `zig build test-unit` (section 11). What remains: a losing `StaticName` spins without yielding while the winner stores 8 bytes, so a winner paused by the OS makes losers burn CPU briefly (no deadlock: the winner never waits on them); the test fakes the Godot calls and covers the SDK caches and `fromComptimeLatin1`, while the generated single-pointer caches are checked by reading the code and by a search of the generated bindings only; and no test has run on real arm64 hardware (cross builds compile only).
18. A game keeps one lock file, and so one open file descriptor, per generation it loaded, until it exits. This is bounded by the number of reloads in one game session, but a very long debug session with many reloads uses one descriptor per reload and could reach the process's open-file limit. The editor does the same: it keeps one open lock file per build it loaded until it exits (section 6). With small modules the 2 GiB warning comes late (about 0.7 MiB per build), so a long tool-script session with about 1000 builds can reach the usual soft limit of 1024 open files; the new build's pin then fails (logged), and other file opens in the editor can fail too. Since Stage 5 a staged build also holds one lock file from staging until the editor loads or drops it.
19. Closed in Stage 5: the game no longer polls the manifest; the editor sends `ziggurat:reload` after each manifest write and when a session starts (section 6, risk 10).
20. Closed in Stage 5: `stage` returns the new generation pinned, the pin travels with the build's outcome until the editor loads or drops it, and pinned generations no longer count toward the 1 GiB byte cap (sections 4 and 6). `max_count` still counts pinned generations, so a tool-script session with many loaded builds keeps fewer old unpinned builds. A generation whose pin cannot be checked (a `.lock` that is a symlink or unreadable) counts as pinned and as a failed delete; the sweep goes on with the others.
21. The Zig download needs about 890 MiB of memory for a few seconds (std xz decodes the release's single 372 MiB block in memory; section 9). On a machine with little free memory the install can fail with out of memory; nothing unchecked is left. Std xz does not verify block checks (CRC) and the zip path does not verify CRC32; integrity rests on the SHA-256 pin and the minisign signature over the whole file, both checked before the unpack, and the tar.xz bytes are hashed again while they are unpacked. The zip bytes are hashed only after the unpack, so a local writer could have changed the file during the unpack and changed it back. Closed on Windows (the zip is the Windows download): the installer opens the zip with read sharing only, so a second handle that asks for write or delete access gets a sharing violation while the install runs (tested under Wine). On Linux the tar.xz is hashed during the unpack, so nothing is left open. Such a writer can already write the user's files. The transfer runs on the main thread at up to 1 MiB per frame, so its speed follows the editor's frame rate.
22. The editor plugin, the highlighter, the debugger plugin, the export plugin and the download exist only in the editor; export builds contain none of them (host tests `export build has no editor plugin` and `export build has no manifest path`, which look for the class names `ZigEditorPlugin`, `ZigExportPlugin` and `ZigReloadCapture`, the mirror list URL, `minisig` and the manifest reader's names in the export library). A game run outside the editor gets no reload (risk 10).
23. Files edited outside Godot are found only at editor focus-in, on the optional interval, or (since Stage 7a) every 2 s while a game from the editor runs, not by an OS watcher. With the interval at 0 and no game running, an external edit waits for focus-in. Two writes of the same size within one file-system timestamp tick look unchanged (section 5). A scan that throws counts as a change, so it rebuilds at every 2 s tick while it keeps failing (as the interval timer already did).
24. A script that names a withheld gdzig Object helper fails to build with a clear message. The compiler reports it at gdzig's generated class file; the diagnostics take the script line from the reference trace (section 13). Since Stage 7a every editor build asks for 16 frames (`-freference-trace=16`, +0.4 % on the median body edit at 300 scripts, section 2), so a helper named three references deep is mapped to the script line (e2e test with a test SDK; no natural three-deep path through the real gdzig was found). When none of the 16 frames is in a project file, the error stays without a script file and line. Export builds keep the compiler's default.
25. **Export build time.** The export compiles the scripts, the SDK and gdzig with LLVM in ReleaseSafe, non-incrementally, on the editor's main thread: the editor shows progress lines but no progress dialog and does not respond until the build ends, and it may first wait up to 120 s for an editor build that holds the build lock. A two-script project took about 8 s cold in the Task 1 prototype and 3.5 s in the install test; a project with hundreds of scripts is not measured, and an LLVM ReleaseSafe build of a large project can take minutes (the Debug session-start build alone took 12.0 s at 300 scripts, section 12). Running the build off the main thread with Godot's progress dialog is later work.
26. **No symbols in exported games.** Export builds have no debug information (`-fstrip`, which makes them deterministic), and so do the export host archive and the packaged editor library. A panic in an exported game, or in the packaged editor library, prints addresses without function names. Since Stage 7a a debug export (`--export-debug`) keeps debug information, at the cost of reproducibility (risk 34). Separate debug files for release exports, if wanted, are later work; `zig build host` still builds a Debug editor library with symbols for development.
27. **The SDK is per target.** Each shipped SDK is staged for one target, and its translate-c output differs per target. Since Stage 7b the package holds one SDK per packaged key (`sdk/x86_64-linux/`, staged for `x86_64-linux-gnu.2.28`, and `sdk/x86_64-windows/`), the editor picks its own and an export the target's (section 5). macOS (Stage 7c) and other architectures need their own stage. Each SDK adds about 161 MB unpacked (risk 31).
28. **Archive normalisation depends on Zig's archive layout.** `tools/ar_normalize.zig` rewrites the export host archive with base-name member names and adjusted symbol-table offsets, so the shipped archive is the same from every checkout and cache folder (section 13). It reads the GNU archive layout and, since Stage 7b, the COFF archive layout that Zig 0.17 writes; a Zig upgrade that changes it makes the tool fail or the archive differ, and the test `package from two cache folders outside the checkout` would catch a difference. Since Stage 7a two members with the same base name and a second long-name table are refused with a sentence that names the problem (the archive has one member today).
29. **Licence of shipped code.** `oopz` had no licence and is replaced by our own clean-room class checks (patch 4, section 13). They were written from gdzig's call sites and tests, so a case gdzig's tests do not cover may behave differently from `oopz` (for example a `*const` class pointer, which counts as a class pointer here). Compile-error cases cannot run as unit tests; they were checked by hand and are listed in `vendor/gdzig/PATCHES.md` so an update can repeat them. The compile-time cost against `oopz` was not measured. The package ships every third-party notice (section 13); the licences of Godot Engine and godot-cpp were taken from the vendored files at the pinned tags, not re-checked upstream.
30. **A self-referencing `base` crashed the compiler** (closed in the final review of Stage 6). A struct whose `base` field refers to its own type, directly or through another struct, made the class walk of patch 4 recurse without end. The walk now detects the loop and answers "not a class", and a chain of more than 64 classes is a compile error (section 13); unit tests cover a self-referencing and a mutually referencing struct and `opaque`, and a 64-class chain.
31. **Package and install size.** The zip is 29.9 MiB (Stage 7b, two targets; 14.8 MiB in Stage 7a and 13.7 MiB in Stage 6, Linux only); unpacked it is about 330 MB, almost all of it the two SDK copies' gdzig sources (about 160 MB per target after the doc comments are stripped). The export host archives are 1.30 MB (Linux) and 1.28 MB (Windows), the empty game libraries 0.73 MB and 1.01 MB, a two-script Linux game library about 0.75 MB (Stage 6) and a two-script Windows one about 1.04 MB (Stage 7b). `zig build host` installs the SDKs into the project too, and a later install does not remove files an older stage left: unpacking the Stage 7b zip over an older add-on leaves the old flat `sdk/` (about 150 MiB) and the old `bin/libziggurat_host_export.a` and `bin/libziggurat_game_empty.so`, so the README says to delete the old `addons/ziggurat/` first. The Asset Store allows 1 GB per version.
32. **A failed export leaves files.** Godot writes `<game>.x86_64` and `<game>.pck` before the library copy fails, so a failed export leaves an incomplete game in the output folder; the error message and the README say not to ship it. The plugin deletes an earlier export's game library from that folder first, so the incomplete game cannot run old Zig code with the new scenes. An export for a platform other than Linux x86_64 and Windows x86_64 finishes with warnings and without Zig scripts; a headless or CI export of such a preset exits with status 0. A PCK/ZIP or patch export of a project with Zig scripts gives an error but still writes the pack (status 0), because Godot gives an export plugin no way to stop it (section 10). When an old game library can neither be deleted nor have its mode changed (POSIX), or neither deleted nor renamed (Windows), the export ends with errors, and since Stage 7b `_export_end` removes the library Godot copied anyway; only when that delete also fails does the export ship the old library, and the error says so (section 10). The first start of the editor after unpacking the zip is not tested without a pre-created `extension_list.cfg` (Godot #111645); the README asks for a restart after the install.
33. Closed in Stage 7a: **the SDK and the export host archive.** The export takes the SDK from the running build service or the manifest (the project setting `ziggurat/dev/sdk_manifest` can point at another SDK) and the archive from `addons/ziggurat/bin/`. Before Stage 7a a developer SDK of another `sdk_version` exported "successfully" and the game then refused the linked table. Now the export compares the SDK's `sdk_version` with the host's and fails with a sentence that says what to do (section 10). Only the version is compared: a developer SDK with the same version but another ABI layout still exports, and the game refuses its table at load ("Ziggurat refused the module linked into this game: The table layout stamp is …") and runs without scripts, so wrong code still cannot run. A link-time stamp symbol would catch that case too; it is not done.
34. **Debug exports are not reproducible.** A debug export (`--export-debug`) builds the game library with `-fno-strip` (section 10), so it holds absolute paths of the project, the SDK and the cache (Stage 6 counted 14 in a two-script library) and differs per project folder and machine. The export says so in one line. Godot's export dialog has Export With Debug ticked by default, so an export from the dialog leaks the build machine's paths (home folder and user name) unless the user unticks it; the line and the README say so. Release exports stay deterministic and path-free; ship a release export. A Windows debug export ships no paths (the `.pdb` stays in the build cache and the DLL holds only its file name), but it is not tested for reproducibility either.
35. **Windows is tested under Wine only** (Stage 7b, the user's decision of 2026-10-26). Real Windows never ran: file locks, the generation store and its trash fallback (the per-file fallback ran nowhere), Job Objects when Godot itself runs inside a job, deleting and renaming a loaded DLL, paths of 260 characters or more, antivirus scanning and build speed may all behave differently there. Worse, **a Windows editor building Zig scripts is unproven even under Wine**: the Windows `zig.exe` 0.17.0 compiles nothing under Wine 11.19 (section 2), so the tests stop where `zig.exe` starts. Not run anywhere: an editor build and its generation loaded through `LoadLibraryExW` in a game started from the editor, the reload of a running game, the `zig.exe` command lines with a space in the project path, and a Windows editor's export of a project with Zig scripts. What is proven under Wine: a Windows export from the Linux editor runs; the Windows editor loads the host, finds the Zig and prepares the build; it exports a Linux game without scripts; the Windows Zig download; the old-library rule. A Wine that implements the lock call, or one run on real Windows, would close the gap; the end-to-end tests already run the full path when `zig.exe` works.
36. **MinGW runtime exports.** A Zig `x86_64-windows-gnu` DLL exports `_CRT_INIT`, `__mingw_module_is_dll` and `atexit` unless a `.def` file lists the exports (section 2). With the `.def` file and the hidden root, Ziggurat's game DLLs export exactly `ziggurat_host_init`, and the PE check allows no exceptions (Ruling 5-1, section 15). If a Zig upgrade changes the MinGW start-up code so that something new is exported or the module loader is imported, the check refuses the library: every Windows export then fails loudly, never silently.
37. **Apparent sizes on Windows.** The store counts generations on Windows (and macOS) by apparent size, not allocated blocks (section 4). On Linux incremental outputs are sparse (about 2.7 times the non-incremental size), and even the first non-incremental generation measured 238 MB apparent against 199 MB allocated at 300 scripts (section 12). If Windows outputs are sparse too, the 1 GiB cap deletes old unpinned generations earlier than needed; it never deletes a pinned one. Windows builds are LLVM and non-incremental by default; their sparseness was not measured.
38. **`~ziggurat_host.dll` copies.** Godot's Windows editor loads a copy, `addons/ziggurat/bin/~ziggurat_host.dll` (hidden), of the add-on's DLL and leaves it there while it runs; it deletes a left-over copy at the next start (section 2). A user can commit it to version control, or upload it with the add-on. It is harmless to delete when the editor is closed. The README names it and gives a `.gitignore` line; the package is built from the build's own outputs, so it never holds one.
